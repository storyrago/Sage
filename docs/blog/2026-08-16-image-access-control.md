# 방은 잠갔는데 사진은 다 보였다 — 채팅 이미지에 인가 붙이기

> *비공개방을 만들어 놓고도 URL 하나면 뚫리던 구멍을, 프리사인드 URL로 닫은 기록*

## 들어가며

채팅 프로젝트에 비공개방을 만들었다. 방장이 초대 코드를 쥐고, 마음에 안 들면 강퇴하고, 방을 통째로 지울 수도 있다. 인가(authorization)를 한 바퀴 제대로 돌았다고 생각했다.

그런데 어느 날 이런 생각이 들었다.

> "강퇴당한 사람이 그 방에 올라온 사진 URL을 복사해 뒀으면?"

열어봤다. **그대로 보였다.** 강퇴해도, 방을 지워도, 그 사람이 탈퇴해도 보였다.

방문에 자물쇠를 달아놓고 창문을 열어둔 꼴이었다.

## 문제는 버킷이 통째로 공개였다는 것

이미지는 S3에 올린다. 그리고 버킷 정책이 이렇게 돼 있었다.

```json
{
  "Effect": "Allow",
  "Principal": "*",
  "Action": "s3:GetObject",
  "Resource": "arn:aws:s3:::내-버킷/*"
}
```

`Principal: "*"` — **누구든**. 즉 URL을 아는 사람이 곧 열람 권한자였다. 우리 서버는 그 요청을 구경도 못 한다. 브라우저가 S3에 직접 가서 받아오기 때문이다.

> **곁개념 — 왜 서버가 모르나**
> 우리가 `<img src="https://버킷.s3.../사진.png">`를 내려주면, 그 URL로 사진을 받아오는 건 **브라우저**다. 우리 서버를 거치지 않는다. 그래서 "이 사람이 그 방 멤버인가"를 물어볼 기회 자체가 없다.

## 첫 번째 생각: 서버가 대신 받아서 넘겨주면 되잖아

가장 먼저 떠오른 건 프록시였다. 버킷을 비공개로 잠그고, 이미지 요청을 우리 서버가 받는다.

```
GET /api/images/{키}  →  서버가 "이 사람 그 방 멤버?" 확인  →  S3에서 읽어서 그대로 넘겨줌
```

깔끔해 보였다. 매 요청마다 인가를 하니 강퇴하면 그 즉시 막힌다.

**그런데 안 됐다.**

우리 앱은 로그인하면 JWT를 받아 저장해 두고, API를 부를 때마다 헤더에 실어 보낸다.

```
Authorization: Bearer eyJhbGciOi...
```

그런데 `<img src="...">`는 **이 헤더를 실을 수 없다.** 이미지 태그가 만드는 요청은 우리 JS가 만드는 게 아니라 브라우저가 알아서 보내는 것이라, 우리가 헤더를 끼워 넣을 자리가 없다.

빠져나갈 길을 셋 생각해 봤는데 전부 별로였다.

- **URL 뒤에 토큰을 붙인다** (`?token=eyJ...`) → 자격증명이 브라우저 히스토리와 서버 로그에 그대로 남는다. 안 된다.
- **`fetch`로 받아서 화면에 꽂는다** → 되긴 한다. 대신 프론트를 전부 뜯어고쳐야 하고, 브라우저 이미지 캐시를 못 쓴다.
- **쿠키로 바꾼다** → 인증 방식 자체를 갈아엎는 일이다. 이미지 하나 때문에 할 일이 아니다.

## 그래서 프리사인드 URL

프록시가 막히자 다른 길을 봤다. **프리사인드(pre-signed) URL**이다.

개념은 단순하다. 버킷은 잠가두고, **서명이 붙은 URL**을 그때그때 만들어 준다.

```
https://버킷.s3.../rooms/1/사진.png
  ?X-Amz-Algorithm=AWS4-HMAC-SHA256
  &X-Amz-Expires=3600
  &X-Amz-Signature=6f2a...
```

이 URL은 **한 시간 동안만** 유효하다. 시간이 지나면 S3가 거절한다.

> **비유하자면 기간 한정 초대권이다.**
> 예전 방식은 "이 주소를 아는 사람은 누구나 입장"이었다. 지금은 "이 초대권을 가진 사람만, 오늘까지만 입장"이다. 초대권은 우리 서버만 발급할 수 있다.

무엇보다 서명이 **URL 안에** 들어가 있어서, `<img src>`가 그대로 동작한다. 헤더가 필요 없다. 프론트 렌더링 코드를 한 줄도 안 고쳤다.

이미지 트래픽이 여전히 S3에서 직접 나가는 것도 좋았다. 1GB짜리 작은 서버를 파일 서버로 만들지 않아도 된다.

### 프로필 사진은 일부러 공개로 남겼다

전부 서명하려다 멈췄다. 서명 URL은 **만들 때마다 값이 달라진다.** 그러면 브라우저가 "이거 아까 받은 그 이미지네"를 알 수 없어서 **매번 다시 받는다.**

채팅 이미지는 한 번 보고 마니까 괜찮다. 그런데 프로필 사진은 메시지마다 반복해서 나온다. 50개를 불러오면 같은 아바타를 50번 다시 받는 셈이다.

그래서 키를 용도별로 나눴다.

| 용도 | 키 | 접근 |
|---|---|---|
| 프로필 사진 | `profiles/...` | 공개 |
| 채팅 이미지 | `rooms/{보낸사람}/...` | 서명 필요 |

버킷 정책도 `profiles/*`만 공개로 좁혔다. 프로필 사진은 어차피 다른 참가자에게 보여주려고 올리는 것이라 민감도가 낮다고 판단했다.

## 인가는 새로 만들지 않았다

여기서 좀 신이 났던 부분이다.

"서명된 URL을 누구에게 줄 것인가"를 판단하려면 인가가 필요한데, **이미 있었다.**

이미지 URL이 사용자에게 닿는 경로는 하나뿐이다. **메시지**다. 그리고 메시지를 읽으려면 이미 그 방 멤버여야 한다.

- REST로 목록을 부르면 → 멤버가 아니면 `NOT_JOINED_ROOM`
- STOMP로 구독하면 → 멤버가 아니면 구독 자체가 거부

즉 **서명된 URL을 받았다는 것 자체가 그 방 참가자라는 뜻**이다. 이미지-방 매핑 테이블도, 업로드할 때 방을 지정하는 것도 필요 없었다. 응답을 만들 때 서명만 붙이면 끝이었다.

```java
public MessageResponse of(Message message) {
    MessageResponse response = MessageResponse.from(message);
    response.setImageUrl(s3Service.presignedGetUrl(response.getImageUrl(), IMAGE_URL_TTL));
    return response;
}
```

여기서 한 가지 조심할 게 있었다. `MessageResponse`를 만드는 곳이 **다섯 군데**였다(메시지 보내기·목록·수정·삭제, 그리고 STOMP 전송). **한 곳이라도 빠뜨리면 그 경로의 이미지만 조용히 안 보인다.** 에러도 안 난다. 그래서 생성 지점을 위 팩토리 하나로 몰아두고, 다섯 곳을 하나씩 되돌려 보며 그때마다 테스트가 빨개지는지 확인했다.

## 그런데 구멍이 남아 있었다

여기까지 하고 "끝났다" 했는데, 마지막 점검에서 걸렸다.

메시지를 보낼 때 이미지 URL은 **클라이언트가 보내는 값**이다.

```java
messageService.create(content, messageRequest.getImageUrl(), memberId, chatroomId, replyToId);
```

이걸 검증 없이 저장하고 있었다. 그리고 응답을 만들 때 저장된 값을 **그대로 서명해서** 돌려준다.

무슨 뜻이냐면,

1. 강퇴당한 사람이 예전에 본 이미지 URL을 갖고 있다
2. **자기 방을 하나 만든다** (누구나 만들 수 있다)
3. 그 URL을 `imageUrl`로 해서 메시지를 보낸다
4. 서버가 **새 서명을 붙여서 돌려준다**
5. 3~4를 원하는 만큼 반복한다

방에서 쫓아내도, 방을 지워도, 계정만 살아 있으면 계속 통한다. **회수가 안 되는 것이다.**

기간 한정 초대권을 만들어 놨는데, 창구에 가면 아무나 무제한으로 재발급해 주고 있었던 셈이다.

고친 방법은 단순했다. **키에 올린 사람을 넣고, 자기 것이 아니면 거절한다.**

```java
// 업로드할 때
rooms/{올린사람}/{uuid}_{파일명}

// 메시지를 만들 때
if (key != null && !key.startsWith("rooms/" + memberId + "/")) {
    throw new CustomException(ErrorCode.INVALID_IMAGE_REFERENCE);
}
```

재서명을 받아도 **자기가 올린 것**만 나온다. 이미 원본 파일을 갖고 있는 사람에게만 열리는 셈이라 의미가 없다.

이 가드가 든든한 이유는 사실 문자열 검사 자체가 아니었다. **"저장을 허용할까"와 "서명을 해줄까"를 같은 함수에서 판단**하게 해뒀기 때문이다. 그래서 이상한 형태의 URL로 가드를 피해도, 그건 서명도 같이 피한다 — 서명 없는 죽은 URL이 저장될 뿐 새 초대권은 못 얻는다. 이 성질은 테스트로 고정해 뒀다. 나중에 URL 파싱을 손볼 때 둘이 어긋나면 구멍이 조용히 되살아나기 때문이다.

## 검증

프로덕션에서 직접 확인했다.

**채팅 이미지를 올리고, 서명 없이 그 주소로 접근:**

```
$ curl -o /dev/null -w "%{http_code}" "https://버킷.s3.../rooms/1/....png"
403
```

**같은 이미지를 메시지로 보내고, 응답에 실려 온 서명 URL로 접근:**

```
$ curl -o /dev/null -w "%{http_code}" "https://버킷.s3.../rooms/1/....png?X-Amz-Signature=..."
200
```

**남의 키를 내 메시지에 실어 보내기:**

```
$ curl -X POST .../messages -d '{"imageUrl":"https://버킷.s3.../rooms/9999/훔친사진.png"}'
{"code":"INVALID_IMAGE_REFERENCE","message":"사용할 수 없는 이미지입니다."}
```

**프로필 사진은 서명 없이도:**

```
200
```

## 배운 것

- **인가는 기능마다 따로 있는 게 아니라 "데이터가 나가는 모든 경로"에 있어야 한다.** 방에 자물쇠를 달아도 사진이 다른 문으로 나가면 잠근 게 아니다.
- **정석이 항상 가능한 건 아니다.** 매 요청 인가(프록시)가 제일 깔끔한데 `<img>`가 헤더를 못 실어서 못 썼다. 못 쓰는 이유를 알고 차선을 고르는 것과, 몰라서 차선에 도달하는 것은 다르다.
- **"기존 인가를 물려받으면 된다"는 절반만 맞았다.** 읽는 쪽은 그게 맞는데, **쓰는 쪽에서 클라이언트가 값을 밀어 넣을 수 있다는 걸 놓쳤다.** 사용자 입력이 그대로 권한 판단의 재료가 되면 거기가 구멍이다.
- **보안 가드는 "무엇을 막는가"보다 "왜 우회할 수 없는가"가 중요하다.** 두 판단을 같은 근거에서 파생시켜 두면, 우회하려는 시도가 자동으로 다른 쪽에서도 막힌다.
- **한 곳만 빠뜨려도 조용히 깨지는 자리**는 생성 지점을 하나로 모으고, 하나씩 되돌려 보며 테스트가 실제로 빨개지는지 확인해야 한다. 초록불은 "테스트가 있다"는 뜻이지 "지켜준다"는 뜻이 아니다.

## 마무리

이 프로젝트는 여기서 일단락한다. 처음엔 "채팅이 되는 것"이 목표였는데, 하다 보니 실시간·인증·인가·배포·관측까지 한 바퀴를 다 돌게 됐다.

마지막 작업이 이미지 접근 제어였던 게 어쩐지 맞는 마무리 같다. **기능을 다 만들어 놓고도, 정작 그 기능이 지키려던 걸 다른 문으로 흘리고 있었다**는 걸 마지막에 발견했으니까.
