# 파이프라인은 초록불인데 옛날 코드가 돌고 있었다 — 실패로 배운 배포기(3)

카카오 로그인을 develop에 머지했다. GitHub Actions는 초록불이었다. 그런데 사이트에 들어가 보니 **카카오 버튼이 없었다.**

새로고침해도 없었다. 캐시를 지워도 없었다. 그리고 채팅 화면으로 넘어가려니 `/api/*`가 전부 **502**를 뱉었다.

배포는 성공했다고 기록돼 있는데, 서버에는 옛날 코드가 돌고 있었다.

## 무슨 일이 있었나

Actions 실행 목록을 보니 답이 있었다. 두 실행이 겹쳐 있었고, **먼저 시작한 옛 커밋의 실행이 더 늦게 끝나 있었다.**

```
옛 커밋의 실행        시작 ─────────────────────▶ 완료   ← 나중에 끝났다
카카오 로그인 실행         시작 ────────▶ 완료
```

빌드 잡은 이미지를 두 개의 태그로 push하고 있었다.

```
ghcr.io/.../app:<커밋 SHA>
ghcr.io/.../app:latest       ← 매번 이걸 덮어쓴다
```

그리고 배포 잡은 `docker compose pull`로 **`:latest`만** 받고 있었다.

그러니 결과는 하나다. **마지막에 끝난 실행이 이긴다.** 나중에 끝난 옛 커밋의 실행이 `:latest`를 덮어썼고, 그 이미지가 그대로 배포됐다.

## 왜 두 가지가 동시에 깨졌나

프론트는 단순했다. 카카오 버튼이 없는 번들이 올라갔으니 버튼이 없다.

백엔드가 502였던 이유는 조금 더 고약했다. 그 사이에 **DB 마이그레이션은 이미 적용된 상태**였다. `V5`가 `google_sub` 컬럼을 지웠다. 그런데 배포된 옛날 코드의 엔티티는 아직 그 컬럼을 매핑하고 있었다.

```yaml
jpa:
  hibernate:
    ddl-auto: validate   # 엔티티와 스키마가 다르면 기동 거부
```

`validate`는 제 일을 했다. 엔티티와 실제 스키마가 어긋났으니 애플리케이션이 **기동에 실패**했다. 컨테이너는 떴다 죽기를 반복했고, nginx는 뒤에 아무도 없으니 502를 냈다.

즉 **스키마는 앞으로 가 있고 코드만 뒤로 간 상태**였다. 롤백이라고 부르기도 애매한, 반쪽짜리 과거였다.

## `concurrency`를 걸어놨는데도

워크플로에는 이미 이게 있었다.

```yaml
concurrency:
  group: deploy
  cancel-in-progress: true
```

이걸 믿고 있었다.

> "겹치면 알아서 앞엣것을 취소하니까 순서가 뒤집힐 일은 없겠지."

아니었다. `cancel-in-progress`는 **새 실행이 시작될 때 진행 중인 실행을 취소한다.** 큐에서 대기하다 뒤늦게 시작되거나, 실패한 잡을 나중에 재실행하는 경우는 이 규칙 밖이다. 그리고 이번엔 취소가 아예 안 걸릴 타이밍이었다.

**동시성 제어는 "겹침"을 다루지 "완료 순서"를 보장하지 않는다.** 이 둘을 같은 것으로 생각한 게 착각이었다.

## 결함은 셋이었다

사고를 뜯어보니 문제가 하나가 아니었다.

| # | 결함 | 결과 |
|---|---|---|
| 1 | 빌드는 `:latest`와 `:sha` 둘 다 push, 배포는 `:latest`만 pull | 마지막에 끝난 실행이 이긴다 |
| 2 | EC2가 compose 파일을 `git reset --hard origin/develop`으로 가져온다 | 이미지와 설정이 서로 다른 커밋에서 올 수 있다 |
| 3 | `docker compose up -d`가 성공하면 잡도 성공 | 컨테이너가 죽어도 초록불이다 |

1번이 사고를 냈고, 3번이 사고를 **숨겼다.** 2번은 아직 안 터졌을 뿐 같은 종류다.

## 고친 것

### ① 배포 단위를 커밋 SHA로 고정한다

`:latest`를 배포 경로에서 완전히 걷어냈다.

```yaml
# docker-compose.yml
image: ghcr.io/.../app:${IMAGE_TAG:?IMAGE_TAG required}
```

`:?`는 "값이 없으면 즉시 실패하라"는 뜻이다. 기본값을 주지 않은 게 핵심이다. **기본값이 있으면 언젠가 조용히 그리로 흐른다.** 배포 스크립트는 자기가 방금 빌드한 SHA만 넘긴다.

```bash
export IMAGE_TAG="$DEPLOY_SHA"
docker compose pull
docker compose up -d --remove-orphans
```

`:latest` push 자체는 남겼다. 최신 표식으로는 여전히 쓸모가 있고, 배포가 더는 그걸 보지 않으니 해롭지 않다.

### ② compose 파일도 같은 SHA에서 가져온다

```bash
# 변경 전
git reset --hard origin/develop   # 브랜치 끝 — 이미지와 다른 커밋일 수 있다

# 변경 후
git reset --hard "$DEPLOY_SHA"    # 이미지와 같은 커밋
```

이미지와 설정이 항상 한 커밋에서 오게 됐다.

### ③ 배포 대상이 develop **끝**인지 검사한다

여기가 제일 헷갈렸던 부분이다. 처음엔 이렇게 생각했다.

> "이 커밋이 develop의 조상인지 확인하면 되겠네."

**그러면 이번 사고를 못 잡는다.** 사고를 낸 그 옛 커밋은 develop의 **조상이 맞기 때문이다.** 옛 커밋은 언제나 조상이다.

물어야 할 것은 "이게 develop에 속하나"가 아니라 **"이게 지금 develop의 끝인가"**였다.

```bash
TIP=$(git rev-parse origin/develop)
if [ "$TIP" != "$DEPLOY_SHA" ]; then
  echo "배포 중단: 이 실행의 커밋 $DEPLOY_SHA 는 develop 최신 $TIP 이 아니다."
  exit 1
fi
```

대가가 하나 있다. 짧은 간격으로 두 번 푸시하면 뒤처진 실행이 **빨간불**이 된다. 그런데 그건 사실 그대로다 — 그 실행은 정말로 배포하지 않았다. 초록불로 위장하는 것보다 낫다고 보고 그냥 뒀다.

그리고 이 가드는 실제로 걸렸다. 이걸 넣은 그날, 연달아 푸시한 실행 하나가 이렇게 멈췄다.

```
배포 중단: 이 실행의 커밋 48dfe228... 는 develop 최신 7fde1905... 이 아니다.
```

전 같으면 이 실행도 조용히 초록불로 끝나고, 옛 이미지가 올라갔을 것이다.

### ④ "떴다"가 아니라 "살아 있다"를 확인한다

`docker compose up -d`는 컨테이너를 **시작**했다는 뜻이지 애플리케이션이 **동작한다**는 뜻이 아니다. 이번 사고에서 정확히 그 틈으로 빠져나갔다.

actuator를 붙이고 컨테이너에 헬스체크를 걸었다.

```yaml
healthcheck:
  test: ["CMD", "curl", "-sf", "http://localhost:8080/actuator/health"]
  interval: 10s
  timeout: 3s
  retries: 12
  start_period: 30s
```

배포 스크립트는 `app`과 `web`이 각각 `healthy`가 될 때까지 기다리고, **컨테이너가 없거나 `unhealthy`이거나 타임아웃이면 해당 서비스 로그 마지막 50줄을 출력하고 잡을 실패시킨다.**

로그를 함께 뱉게 한 건 의도적이다. 빨간불만 뜨고 이유를 찾으러 EC2에 접속해야 한다면 절반만 고친 것이다.

여기에 하나 더 붙였다. 컨테이너 헬스체크는 컨테이너 **안에서** `localhost`로 검사하기 때문에, DNS나 TLS 인증서나 포트 바인딩이 깨져도 healthy로 잡힌다. 그래서 배포가 끝난 뒤 러너에서 **공개 URL로** 한 번 더 확인한다. 사용자가 실제로 들어오는 경로다.

```
스모크 통과: / =200, /api/chatrooms=302, /actuator/health=404
```

마지막 줄이 404인 게 맞다. actuator를 외부로 열 생각은 없고, 다만 **SPA 폴백이 걸려 200 HTML을 반환하던 것**을 끊었다. 앱이 죽어 있어도 200이 나오면 그것대로 오판을 부른다.

## 검증

- `docker compose config`로 `IMAGE_TAG`가 없을 때 실제로 실패하는지 확인했다. 폴백이 남아 있으면 이 모든 게 무의미하다.
- 배포 후 EC2에서 실행 중인 이미지 태그가 정말 그 SHA인지 확인했다.
- 짧은 간격으로 두 번 푸시해, 뒤처진 실행이 "develop 최신이 아니다"로 중단되는 것을 봤다.

## 남은 것

이 헬스 게이트는 나중에 한 번 더 손봐야 했다. 기본 헬스 인디케이터에는 Redis가 포함되는데, 이 앱은 Redis가 죽어도 API가 계속 응답하도록 만들어져 있다. 그대로 두면 **Redis 장애가 배포를 통째로 막고, 정작 그 장애를 고치는 배포조차 나가지 못한다.** 지금은 게이트를 `readiness` 그룹으로 옮기고 `db`·`diskSpace`만 남겨뒀다.

## 마무리

배운 것 두 가지.

첫째, **가변 태그는 배포 단위가 아니다.** `:latest`는 "최신 커밋"이 아니라 "마지막에 끝난 실행"이다. 평소엔 둘이 같아 보이니 구분할 이유를 못 느끼는데, 어긋나는 순간 어느 코드가 돌고 있는지 아무도 모르게 된다. 배포하는 것이 무엇인지 이름으로 못 박아야 한다.

둘째, **검증하지 않는 파이프라인은 사고를 숨긴다.** 이번에 제일 무서웠던 건 옛 코드가 배포된 것 자체가 아니라, 그게 **초록불로 기록됐다는 것**이다. 실패했는데 성공했다고 말하는 파이프라인은 없는 것보다 나쁘다. 파이프라인이 초록이라고 말할 수 있는 건 "실행이 끝났다"까지이고, "배포가 살아 있다"는 따로 확인해야 얻는다.
