# 소셜 로그인을 하나 더 붙였더니 — 이메일은 식별자가 아니었다

구글 로그인은 이미 붙여둔 상태였다. 여기에 카카오 로그인을 추가하는 건 설정 몇 줄이면 될 거라 생각했다. 실제로는 **회원 테이블의 스키마를 바꾸고, 실시간 알림이 사용자를 찾는 방식까지 손봐야** 했다.

두 번째 소셜 로그인을 붙이면서 비로소 드러난 설계 결함에 대한 기록이다.

## 구글만 있을 땐 문제가 없었다

당시 회원 테이블은 이랬다.

```sql
email       VARCHAR(255) NOT NULL UNIQUE,
google_sub  VARCHAR(255) NULL UNIQUE,   -- 구글이 주는 고유 ID
```

그리고 실시간 안읽음 알림은 이메일로 사용자를 찾아 보내고 있었다.

```java
messagingTemplate.convertAndSendToUser(member.getEmail(), "/queue/unread", event);
```

잘 돌아갔다. 구글은 **항상 이메일을 주기 때문**이다. 이메일이 있고, 유일하고, 잘 안 바뀌니 식별자로 써도 아무 일이 없었다.

문제는 그게 **구글이라서 그랬던 것**이지, 원래 그런 게 아니었다는 점이다.

## 카카오가 드러낸 두 가지

### 1. 카카오는 이메일을 안 준다

카카오에서 이메일을 받으려면 `account_email` 동의항목이 필요한데, 이건 **비즈니스 인증을 받은 앱에만 열린다.** 개인 개발자 앱에서는 콘솔에 "권한 없음"으로 표시되고 설정 버튼조차 없다.

![카카오 동의항목 - 이메일 권한 없음](이미지_URL)

받을 수 없는 동의항목을 요청하면 인가 요청 자체가 거부된다.

```
잘못된 요청 (KOE205)
```

그럼 이메일 없이 회원을 만들면 되는데 — `email`이 `NOT NULL`이었다. **회원 생성 자체가 불가능했다.**

### 2. 이메일은 변한다

더 근본적인 문제는 이쪽이었다. 코드를 다시 보니 이런 게 있었다.

```java
if (email != null && !email.equals(member.getEmail())) {
    member.updateEmail(email);   // 구글 계정 이메일이 바뀌면 갱신
}
```

이메일이 바뀔 수 있다는 걸 **이미 알고 그 코드를 짜놨으면서**, 동시에 그 값을 실시간 알림의 식별자로 쓰고 있었던 것이다. 사용자가 이메일을 바꾸는 순간 알림이 엉뚱한 곳을 향하게 되는 구조였다.

## 식별자를 옮기다

두 문제의 뿌리는 하나였다. **이메일을 신원으로 쓴 것.**

그래서 신원을 두 군데로 옮겼다.

**① DB의 신원: `(provider, provider_id)`**

```sql
-- 변경 전
google_sub VARCHAR(255) UNIQUE          -- 구글 전용

-- 변경 후
provider    VARCHAR(20),                 -- GOOGLE / KAKAO
provider_id VARCHAR(255),
UNIQUE (provider, provider_id)           -- 둘을 합쳐 하나의 신원
```

`provider_id`는 소셜 제공자가 주는 고유 ID다(OIDC의 `sub`). 이메일이 바뀌어도, 없어도 이 값은 그대로다. 그리고 `email`은 `NULL`을 허용하는 **선택 속성**으로 내려왔다.

**② 실시간 알림의 신원: 회원 번호**

```java
// 변경 전 — 변하고, 없을 수도 있는 값
convertAndSendToUser(member.getEmail(), "/queue/unread", event);

// 변경 후 — 절대 안 변하는 값
convertAndSendToUser(String.valueOf(member.getId()), "/queue/unread", event);
```

## 덤으로 사라진 조용한 버그

이걸 고치고 나서야 알았는데, 원래 코드에는 **터졌어도 아무도 몰랐을 버그**가 있었다.

`convertAndSendToUser`는 첫 번째 인자로 받은 값과 일치하는 세션을 찾아 메시지를 보낸다. 만약 이메일이 `null`이면? **예외도 로그도 없이 그냥 아무에게도 안 간다.** 조용히 실패한다.

구글만 쓰던 시절엔 이메일이 늘 있었으니 드러나지 않았을 뿐, 카카오 회원이 생기는 순간 **그 사람만 안읽음 알림이 안 오는** 상태가 됐을 것이다. 그리고 에러가 없으니 원인을 찾기도 어려웠을 것이다.

식별자를 회원 번호로 옮기면서 이 버그도 같이 사라졌다.

## 그리고 마이그레이션이 놓칠 뻔한 것

여기까지 하고 마이그레이션을 썼다. 기존 구글 회원의 값을 새 컬럼으로 옮기는 작업이다.

```sql
UPDATE members SET provider_id = google_sub WHERE google_sub IS NOT NULL;
```

자연스러워 보인다. `google_sub`이 있으면 구글 회원이니, 그 값을 `provider_id`로 옮기면 끝. **그런데 이게 일부 사용자를 영구히 로그인 불가로 만들 뻔했다.**

옛날 코드를 다시 봤다. 이메일로 가입한 기존 회원이 나중에 구글로 로그인하면, 두 계정을 연결하는 경로가 있었다.

```java
public void linkGoogle(String googleSub) {
    this.googleSub = googleSub;      // google_sub만 채운다
}                                     // provider는 'LOCAL'인 채로 남는다
```

즉 DB에는 **`provider = 'LOCAL'`인데 `google_sub`은 있는 행**이 존재할 수 있었다. 위 마이그레이션은 `provider_id`만 옮기고 `provider`는 `'LOCAL'`로 놔둔다. 그러면 새 조회 조건은:

```java
findByProviderAndProviderId("GOOGLE", sub)   // → 못 찾는다
```

못 찾으니 "처음 오는 사용자"로 판단해 새 계정을 만들려 하고, 이메일이 겹치니 거부당한다. **그 사용자는 자기 계정에 영원히 못 들어간다.** 게다가 이메일/비밀번호 로그인 화면을 이미 없앤 뒤라 대안도 없었다.

고치는 건 한 구절이었다.

```sql
UPDATE members
SET provider_id = google_sub, provider = 'GOOGLE'   -- provider도 함께
WHERE google_sub IS NOT NULL;
```

## 검증

실제 MySQL에 세 가지 경우를 심어놓고 마이그레이션을 돌려봤다.

| 넣은 행 | 기대 | 결과 |
|---|---|---|
| `LOCAL` + `google_sub` 있음 | `GOOGLE`로 이관 | ✅ |
| 순수 `LOCAL` (google_sub 없음) | 그대로 유지 | ✅ |
| 이미 `GOOGLE` | 변화 없음 | ✅ |

그리고 로컬에 백엔드와 프론트를 띄워 실제 계정으로 확인했다. 구글 로그인 → 회원 생성, **다시 로그인 → 계정이 늘어나지 않음**(같은 신원으로 매칭됐다는 뜻), 카카오 로그인 → `email`이 `NULL`인 회원 생성, 그리고 **안읽음 배지 실시간 증가**까지.

마지막 항목이 제일 중요했다. 알림 식별자를 바꿨으니, 어긋났다면 배지가 조용히 안 올랐을 것이기 때문이다.

## 마무리

배운 것 두 가지.

첫째, **변하는 값을 식별자로 쓰면 안 된다.** 이메일은 바뀔 수 있고, 제공자에 따라 아예 없을 수도 있다. 식별자는 불변이어야 하고, 이메일은 그냥 "그 사람에 대해 알고 있는 정보 하나"로 두는 게 맞다. 성숙한 인증 서비스들이 이메일을 선택 속성으로 두는 이유를 이번에 체감했다.

둘째, **마이그레이션을 쓸 때는 스키마가 아니라 그 데이터를 만든 코드 경로를 봐야 한다.** 컬럼 정의만 보면 "`google_sub`이 있으면 구글 회원"이 당연해 보인다. 하지만 그 데이터를 실제로 넣은 코드는 그렇게 쓰지 않았다. 스키마는 데이터가 **어떻게 생겼는지**는 알려주지만, **어떻게 그렇게 됐는지**는 알려주지 않는다.

다음에는 이 과정에서 겪은 배포 사고 — 파이프라인은 초록불인데 옛날 코드가 배포돼 있던 이야기 — 를 정리해 볼 계획이다.
