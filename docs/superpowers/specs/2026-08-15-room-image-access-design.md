# 방 이미지 접근 제어 설계

## 목표

방에 올린 이미지를 그 방의 참가자만 볼 수 있게 한다.

지금은 S3 버킷 정책이 `s3:GetObject`를 전체 공개로 열어두고, DB에는 공개 URL 전문이 저장된다.
프론트는 `<img src>`로 S3에 직접 붙는다. 그래서 **URL을 한 번 받은 사람은 영구히 읽는다** —
강퇴당해도, 방이 삭제돼도, 방을 나가도, 로그아웃해도, 계정이 지워져도 그대로다.

방을 잠그고 강퇴까지 만들어 둔 상태에서 거기 올린 사진이 URL만으로 영구히 읽히는 것은
비공개방 기능 자체와 모순된다.

## 범위

**포함**

- 채팅 이미지를 프리사인드 URL로만 읽게 한다(만료 1시간).
- 프로필 사진은 공개로 유지하되 키 접두사로 분리한다.
- 업로드 검증을 서버에 넣는다.

**제외**

- 프로필 사진 접근 제어 — 참가자에게 노출되는 정보라 민감도가 낮고, 서명하면 아바타 캐시가 깨진다.
- DB에 키가 아니라 URL을 저장하는 구조 — §4에 이유와 대가를 적는다.
- 이미지 원본을 프록시로 스트리밍하는 방식 — §1에 불가능한 이유를 적는다.

## 1. 백엔드 프록시를 쓰지 않는 이유

`GET /api/images/{key}`가 인가 검사 후 S3에서 스트리밍하는 방식은 이 앱에서 성립하지 않는다.
`<img src>`는 `Authorization` 헤더를 실을 수 없고, 이 앱의 인증은 localStorage의 Bearer 토큰이다.

살리려면 셋 중 하나가 필요하고 셋 다 이 작업보다 크다.

- 쿼리스트링에 토큰 — 자격증명이 브라우저 히스토리·서버 로그·리퍼러에 남는다. 채택 불가.
- `fetch`로 blob을 받아 `objectURL` — 프론트 전면 개편, 브라우저 캐시 사용 불가.
- httpOnly 쿠키 도입 — 인증 모델 전체 변경.

그래서 프리사인드 URL을 쓴다. 서명이 URL 안에 있으므로 `<img src>`가 그대로 동작하고,
이미지 트래픽이 S3에서 직접 나가 1GB EC2를 파일 서버로 만들지 않는다.

## 2. 인가는 이미 있는 것을 물려받는다

프리사인드는 인가를 **URL을 만들 때** 한다. 이미지 URL이 사용자에게 도달하는 경로는 메시지뿐이고,
메시지 경로에는 이미 인가가 걸려 있다.

- REST: `MessageService.getMessages`가 비참가자를 `NOT_JOINED_ROOM`으로 막는다.
- STOMP: `/sub/chatrooms/{id}` 구독을 `RoomAuthorizationChannelInterceptor`가 막는다.

**서명된 URL을 받았다는 것은 이미 그 방의 참가자라는 뜻이다.**
따라서 이미지-방 매핑 테이블도, 업로드 시점의 방 바인딩도 필요 없다.

## 3. 키 접두사와 버킷 정책

키는 지금 `{uuid}_{원본파일명}`으로 버킷 루트에 평면이다. 용도별 접두사를 넣는다.

| 용도 | 키 | 접근 |
|---|---|---|
| 프로필 사진 | `profiles/{uuid}_{name}` | 공개 |
| 채팅 이미지 | `rooms/{uuid}_{name}` | 비공개(서명 필요) |

업로드 시점에 용도를 알아야 하므로 `POST /api/images`에 `purpose` 파라미터를 **필수로** 추가한다.
값은 `profile`과 `chat` 둘뿐이고, 그 외 값이나 누락은 400으로 거절한다.
기본값을 두지 않는다 — 기본값이 있으면 용도를 잘못 지정한 업로드가 조용히 공개된다.
프론트 호출 지점은 둘이다(프로필 사진 훅, 채팅 이미지 전송).

버킷 정책은 "버킷 전체 공개"에서 **`profiles/*`만 공개**로 바꾼다. AWS 콘솔에서 하는 수동 작업이다.

## 4. DB에 저장하는 값은 바꾸지 않는다

`messages.image_url`과 `members.profile_image_url`은 지금처럼 전체 URL을 저장하고,
서명할 때 기존 `S3Service.extractKey`로 키를 뽑는다. 마이그레이션이 붙지 않는다.

⚠️ **이것은 정석이 아니다.** 버킷명과 리전이 박힌 URL을 식별자로 쓰고 있어서,
버킷을 옮기거나 리전을 바꾸면 저장된 값이 전부 무효가 된다.
정석은 키만 저장하고 URL은 응답에서 조립하는 것이다.

지금 그것을 하면 DTO 4개(`MessageResponse`·`MemberResponse`·`PublicMemberResponse`·
`ChatRoomMemberResponse`) + 고아 탐지(`ImageReferences`, `MessageRepository.existsByImageUrl`·
`existsByContentContaining`) + 마이그레이션 2벌이 붙어 이번 목표보다 커진다.
**별도 작업으로 남긴다.** 이 선택의 대가는 위에 적은 그대로다.

## 5. 서명

`S3Config`에 `S3Presigner` 빈을 추가한다. AWS SDK v2의 `s3` 모듈에 포함되어 있어 의존성 추가는 없다.

`S3Service.presignedGetUrl(storedUrl, ttl)`의 분기는 셋이다.

| 대상 | 처리 |
|---|---|
| 우리 버킷 URL이 아님 | 원본 그대로 반환(하위호환) |
| `profiles/` 키 | **서명하지 않고 원본 그대로** |
| 그 외(`rooms/`·기존 루트 키) | 1시간 서명 |

두 번째 분기를 빠뜨리면 아바타가 매 응답마다 다른 URL을 받아 브라우저 캐시가 무효화된다.
프로필 사진을 공개로 남기기로 한 이유가 그대로 날아간다.

기존 채팅 이미지는 루트 키 그대로 서명된다. 세 번째 분기가 그것을 덮는다.

### 서명 지점

`MessageResponse.imageUrl` 한 곳이다. 프로필 관련 DTO 4개는 손대지 않는다.

`MessageResponse`를 만드는 곳이 셋이다 — STOMP 신규 발신, REST 목록, REST 수정·삭제.
흩어놓으면 한 곳을 빠뜨리고, 빠뜨린 경로의 이미지는 그냥 보이지 않는다.
공유 컴포넌트 하나로 모으고 세 지점이 그것을 통과하게 한다.

STOMP는 Redis publish **전에** 서명한다. 방송 수신자는 전부 그 방의 참가자이므로 안전하다.

### 만료 시간을 1시간으로 잡는 이유

액세스 토큰 수명과 같다. "세션이 살아있는 동안 유효"로 규칙이 하나가 되고,
토큰이 만료되면 어차피 다시 로그인하며 메시지를 새로 받는다.

더 짧게 잡으면 자리를 비웠다 돌아왔을 때 이미지가 거의 항상 깨진다.
더 길게 잡으면 강퇴당한 사람이 그만큼 오래 접근을 유지한다.

## 6. 만료 대응

화면에 이미 렌더된 `<img>`는 만료된 URL을 들고 있다. `onError`에서 메시지를 다시 불러와 URL을 갱신한다.

**재시도는 한 번만 한다.** 진짜로 깨진 이미지에서 무한 재조회가 돌면 안 된다.
채팅 이미지 렌더 지점은 둘이다(`msg.imageUrl`, 본문에 박힌 URL).

## 7. 업로드 검증

프로필 접두사를 공개로 남기기로 한 직접적인 결과다.

지금 서버는 파일을 검증하지 않고 클라이언트가 보낸 content-type을 그대로 S3에 저장한다.
이미지 여부를 확인하는 것은 프론트(`useProfilePhotoDraft.ts`)뿐이다.
따라서 로그인한 사용자가 공개 접두사에 임의 파일을 올려 AWS 도메인에서 호스팅할 수 있다.
이 표면을 남긴 채로는 "막았다"고 말할 수 없다.

- content-type 화이트리스트: `image/jpeg`·`image/png`·`image/gif`·`image/webp`
- **`ImageIO.read`로 실제 디코딩을 시도**해 이미지가 맞는지 확인한다.
  content-type은 클라이언트가 거짓말할 수 있으므로 이것이 실제 방어다.
  서버 크기 제한이 10MB(`spring.servlet.multipart.max-file-size`)라 비용은 감당된다.
- S3에 저장하는 content-type은 클라이언트 값이 아니라 검증된 값을 쓴다.
- **원본 파일명을 정규화한다.** 키가 `{uuid}_{원본파일명}`이라 파일명이 그대로 URL 경로가 된다.
  경로 문자와 개행이 섞이면 키가 오염된다. 영숫자·점·하이픈만 남긴다.

## 8. 검증

- 단위 — 서명 분기 3종(외부 URL 통과 / `profiles/` 무서명 / `rooms/`·루트 서명)
- 단위 — 업로드 검증(비이미지 거부, content-type 위조 거부, 파일명 정규화)
- 실측 — 서명 없이 `rooms/` 객체 GET → **403**, 서명 URL → 200, **만료 후 → 403**,
  `profiles/` 무서명 → 200
- 기존 백엔드 테스트 그린, 프론트 `npm test`·`lint`·`build`

## 9. 배포 순서

수동 개입이 있고 순서를 지켜야 한다.

1. **코드 배포** — 새 업로드부터 접두사가 적용되고 서명이 동작한다.
   정책이 아직 전체 공개라 이 시점에는 아무것도 깨지지 않는다.
2. **기존 프로필 사진 이관** — `profiles/`로 복사 → `members.profile_image_url` 갱신 → 원본 삭제.
3. **버킷 정책 교체** — `profiles/*`만 공개.

3을 먼저 하면 이관 전 프로필 사진이 전부 깨진다.
기존 채팅 이미지는 옮기지 않는다. 루트에 그대로 두면 새 정책에서 자동으로 비공개가 되고,
서명은 키만 알면 되므로 루트 키도 그대로 서명된다.

롤백은 정책을 되돌리면 즉시 원복된다. 코드는 그대로 두어도 무해하다.

## 10. 알려진 한계

- **서명 URL은 만료까지 공유 가능하다.** 강퇴당한 사람이 직전에 받은 URL을 최대 1시간 쓴다.
  없애려면 매 요청 인가가 필요한데 §1의 이유로 이 앱에서는 불가능하다.
- 프로필 사진은 계속 URL만 알면 누구나 본다. 의도된 선택이다.
- URL을 식별자로 저장하는 구조가 남는다(§4).
- 기존에 유출된 URL은 정책 교체 시점에 무효가 되지만, 그 전에 **내려받아 둔 사본**은 회수할 수 없다.

### 구현 중 발견해 막은 것

설계 당시에는 없던 항목이다. 인가를 메시지 경로에서 물려받는 것만으로는 부족했다.

`MessageRequest.imageUrl`은 클라이언트가 보내는 값이라, 검증 없이 저장하면 응답 팩토리가 그것을
그대로 서명해 준다. 즉 캡처해 둔 URL을 자기 방에 올려 새 서명을 무한히 받는 **재서명 오라클**이 된다.
계정이 살아 있는 한 강퇴·방 삭제와 무관하게 통하므로, 이 기능의 목적이 통째로 무효가 된다.

그래서 채팅 키에 업로더를 넣고(`rooms/{memberId}/{uuid}_{name}`),
`MessageService.create`가 **발신자 소유가 아닌 우리-버킷 키를 거절**한다.

이 가드가 안전한 이유는 문자열 검사 자체가 아니라, **입장 판정과 서명 판정이 같은 `extractKey`에서
파생된다**는 데 있다. 가드를 피하는 URL 형태는 서명도 피하므로, 우회해도 서명 없는 죽은 URL이
저장될 뿐 새 서명을 얻지 못한다. 이 불변식은 테스트로 고정해 두었다 —
`extractKey`를 고칠 때 두 판정이 어긋나면 오라클이 조용히 되살아난다.

### 이번 범위 밖으로 남긴 위험

- **외부 URL을 `imageUrl`로 넣는 것은 여전히 허용된다.** 우리 버킷이 아닌 URL은 통과하므로,
  악의적인 주소를 올리면 그 방 참가자 전원의 IP와 User-Agent가 외부 서버로 샌다.
  이번 변경 이전부터 있던 동작이고, 막으려면 별도 판단이 필요하다.
- **`MemberService.updateProfileImage`는 임의 URL을 검증 없이 받는다.** 프로필은 서명 대상이 아니라
  지금은 무해하지만(깨진 아바타로 끝난다), 나중에 프로필에 서명을 붙이면 가드 없는 싱크가 된다.
- **본문(`content`)에 박힌 이미지 URL은 서명되지 않는다.** 정책 교체 후에는 과거 것도 새로 붙여넣는
  것도 깨진다. 전환 전 개수 측정은 런북에 있다.
- **컨테이너에 `-Xmx`/`MaxRAMPercentage`가 설정돼 있지 않다.** 업로드 치수를 16MP로 제한해
  래스터를 ~64MB로 묶었지만, 힙 상한 자체가 명시되지 않은 것은 그대로다.
