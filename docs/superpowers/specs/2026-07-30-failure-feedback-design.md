# 실패를 사용자에게 알리기 설계

- 작성일: 2026-07-30
- 범위: `frontend/` 전용. **백엔드 변경 없음.**
- 선행 문서: `docs/superpowers/specs/2026-07-30-ui-audit.md` §2 (감사에서 드러난 실패 무음 6곳)

## 1. 배경과 목표

감사에서 확인된 것은 "죽은 버튼"이 아니라 **말 없는 실패**였다. 핵심 경로마다 실패가 `console.error`로 삼켜지거나 아예 잡히지 않는다.

| 기능 | 현재 |
|---|---|
| 메시지 전송 | `try/catch`가 없다. 입력창은 이미 비워져 사용자는 보냈다고 믿는데 글이 증발한다 |
| 채널 만들기 | `catch`가 없다. 버튼만 원상복구되어 먹통으로 보인다 |
| 방 입장·메시지 로드 | `console.error`만. 빈 방으로 위장된다 |
| 참가자 목록 | 실패 시 빈 배열로 만들어 `참가자가 없습니다`로 **위장한다** |
| 이미지 업로드 | `console.error`만. 스피너가 조용히 사라진다 |
| 이전 메시지 로드 | `console.error`만. 무한 스크롤이 조용히 멈춘다 |

한편 메시지 수정·삭제는 `alert()`로 알린다. **같은 앱에서 처리가 갈린다** — 정책이 없고 그때그때 처리된 결과다.

목표는 두 가지다.

1. **유실을 막는다** — 특히 메시지 전송. 실패해도 사용자가 쓴 글이 사라지면 안 된다
2. **실패를 보이게 한다** — 성공한 것처럼 보이거나 다른 정상 상태로 위장하지 않는다

## 2. 결정 사항

**D1. 메시지 전송은 실패 시 입력 내용을 되돌린다.**
전송은 낙관적 렌더가 아니다. 서버가 브로드캐스트로 돌려줘야 화면에 나타나는데, 입력창은 `onSendMessage` 직후 즉시 비워진다(`ChatArea.tsx`의 `handleSend`). 실패하면 글이 증발한다.

`onSendMessage`가 `Promise`를 반환하게 바꾸고, `ChatArea`가 결과를 기다렸다가 실패하면 **입력 내용을 복원**하고 입력창 위에 오류를 표시한다. 사용자는 그대로 다시 보내면 된다.

*대안이었던 것*: 낙관적 렌더 + 전송중·실패 상태 + 재시도(카카오톡·슬랙 방식). 어떤 메시지가 실패했는지 정확히 보이고 순서도 유지되지만, 임시 ID를 만들고 서버 브로드캐스트가 돌아왔을 때 **중복 제거**를 해야 한다. STOMP 응답에는 클라이언트 임시 ID가 없어 매칭 규칙을 따로 정해야 하고, 잘못 짜면 메시지가 두 번 보이거나 사라지는 새 버그가 된다. 유실 방지가 먼저이므로 이번에는 하지 않는다(§5).

**D2. 표시 수단은 "보고 있는 곳"에 맞춘다.**
공용 토스트를 하나 만들되, 폼이나 패널을 보고 있는 실패는 그 자리에 인라인으로 표시한다. 토스트는 붙일 자리가 없는 실패에만 쓴다.

| 실패 | 표시 |
|---|---|
| 메시지 전송 | 입력 내용 복원 + 입력창 위 인라인 오류 |
| 채널 만들기 | 다이얼로그 안 인라인 (설정 화면의 닉네임 오류와 같은 방식) |
| 참가자 목록 | 패널 안 "불러오지 못했어요 · 다시 시도" |
| 방 입장 | 토스트 + 랜딩 복귀 (D3) |
| 메시지 로드 | 토스트 + 채팅 화면 유지 (D3) |
| 이미지 업로드 | 토스트 |
| 이전 메시지 로드 | 토스트 |

**D3. 방 입장 실패와 메시지 조회 실패를 구분한다.**
지금은 입장이 실패해도 화면이 이미 채팅으로 넘어가 빈 방에 갇힌다.

- **`joinChatRoom` 실패** → 토스트 + `selectedChannelId`를 비워 **랜딩으로 되돌린다.** 방에 못 들어갔으므로 채팅 화면에 남을 이유가 없다.
- **`getMessages` 실패** → 채팅 화면에 남고 토스트로 알린다. 입장 자체는 성공했으므로 되돌리면 과하다.

*대가*: 두 경로를 나누느라 `loadMessages`의 오류 처리가 갈린다. 단순히 "실패하면 무조건 복귀"보다 코드가 길다.

**D4. 토스트는 동시에 하나만 띄운다.**
새 토스트가 이전 것을 대체한다. 하단 중앙, 4초 후 자동으로 사라지고 클릭하면 즉시 닫힌다. 여러 개를 쌓는 큐는 만들지 않는다 — 지금 필요 없다.

**D5. 토스트 상태는 App이 들고, 배선은 prop으로 한다.**
토스트를 띄우는 곳은 셋인데 **둘은 App 자신**(방 입장·이전 메시지 로드)이고 `ChatArea` 하나만 prop이 필요하다(이미지 업로드). Context를 새로 도입할 규모가 아니다.

**D6. 기존 `alert()` 두 곳을 없앤다.**
메시지 수정·삭제 실패가 `alert()`을 쓴다. 동작은 하지만 조악하고, 이번에 만드는 수단과 이중이 된다.

- **삭제 실패** → 토스트. 입력창과 무관한 조작이다.
- **수정 실패** → 전송과 같은 인라인 처리. 수정도 입력창에 글을 쓰는 조작이라, 실패했는데 고쳐 쓴 내용이 사라지면 D1의 목표("유실을 막는다")가 수정 경로에서만 깨진다. `onEditMessage`도 `Promise`를 반환하게 하고 `ChatArea`가 실패를 받아 입력과 수정 상태를 되돌린다.

**D7. 사용자에게 보이는 문구는 헬퍼를 거친다.**
`err.message`를 그대로 노출하면 네트워크 실패의 `Failed to fetch`, 배포 중 nginx 502 HTML 원문, `message` 필드가 없는 JSON 원문이 그대로 사용자에게 보인다. `TypeError`는 네트워크 문구로 바꾸고, 길거나 HTML·JSON처럼 보이는 원문은 한국어 fallback으로 대체한다(`lib/errors.ts`).

## 4. 동작

```
메시지 전송
  ChatArea.handleSend → await onSendMessage(...)
    성공 → 입력창 비운 상태 유지
    실패 → 입력 내용 복원 + 입력창 위 오류 표시

채널 만들기
  ChannelLanding.submit → await onCreateChannel(name)
    실패 → 다이얼로그 안 오류 표시. 다이얼로그는 열린 채, 입력값 유지

방 선택
  App: joinChatRoom 실패  → 토스트 + selectedChannelId='' (랜딩 복귀)
       getMessages 실패   → 토스트. 채팅 화면 유지

참가자 패널 열기
  ChatArea.openMembers 실패 → 패널 안 "불러오지 못했어요 · 다시 시도"

이미지 업로드 / 이전 메시지 로드 / 메시지 수정·삭제
  실패 → 토스트
```

## 5. 남는 것

- **STOMP가 연결된 상태에서 서버가 거절하면 여전히 조용하다.** `stomp.send()`는 ack를 기다리지 않는 fire-and-forget이라 클라이언트가 실패를 알 방법이 없다. 이번 범위가 잡는 것은 **STOMP 미연결 → REST 폴백 실패** 경로다. 연결이 끊겼을 때가 실제 사고 지점이므로 실익은 크지만, 서버 거절까지 잡으려면 D1의 대안(낙관적 렌더 + 임시 ID + 중복 제거)이 필요하다.
- **여러 메시지를 연속으로 보내다 중간 것이 실패하면 순서가 어색해진다.** 복원된 글이 입력창으로 돌아오므로 나중에 보낸 것보다 뒤에 전송된다. D1의 대안이 해결하는 문제다.
- 토스트에 큐가 없어 짧은 시간에 두 개가 발생하면 앞의 것을 못 볼 수 있다.
