# 프론트 전수 감사 — 죽은·가짜 UI 색출 결과와 처리 결정

- 작성일: 2026-07-30
- 대상: `frontend/src/` 전체(8파일 2,318줄) + 대응 백엔드 엔드포인트
- 방법: 요소 → 핸들러 → `App.tsx` prop → `lib/api.ts`/`lib/stomp.ts` → `src/main/java/` 컨트롤러·서비스까지 추적. 네 갈래로 나눠 병렬 조사 후 교차 확인.

## 1. 판정 기준

| 분류 | 뜻 |
|---|---|
| **진짜** | 백엔드에 반영되고 새로고침 후에도 유지된다 |
| **가짜** | 반응하지만 `localStorage`나 로컬 state만 바꾼다 |
| **죽음** | 아무 일도 하지 않는다 |
| **반쪽** | 동작은 하는데 실패해도 사용자에게 안내가 없다 |

로컬 저장이 **설계상 맞는 것**은 가짜로 세지 않았다. 테마 토글(기기 단위 설정)과 로그아웃(JWT 무상태라 서버 폐기 호출이 없는 게 정상)이 여기 해당한다.

## 2. 가장 큰 발견 — 문제는 "죽은 버튼"이 아니라 "말 없는 실패"였다

감사 착수 시 예상은 "눌리지만 아무 일도 안 하는 버튼"이었다. 실제로 죽은 것은 하나뿐이었고, **핵심 경로마다 실패가 조용히 삼켜지고 있었다.**

| 기능 | 위치 | 실패 시 사용자가 보는 것 |
|---|---|---|
| 메시지 전송 | `App.tsx:355` `handleSendMessage` | 아무것도. 입력창은 이미 비워져 보낸 것으로 보이고 메시지는 유실된다 |
| 채널 만들기 | `App.tsx:510` + `ChannelLanding.submit` | 버튼만 원상복구. 이유 없이 먹통으로 보인다 |
| 방 입장·메시지 로드 | `App.tsx:215` | 빈 방으로 위장된다. 대화가 없는 것인지 로드 실패인지 구분 불가 |
| 참가자 목록 | `ChatArea.openMembers` | `참가자가 없습니다`로 위장된다 |
| 이미지 업로드 | `ChatArea:203` | 스피너만 사라진다 |
| 무한 스크롤 | `App.tsx:404` | 조용히 멈춘다 |

메시지 전송이 가장 나쁘다. REST 폴백은 **STOMP가 끊겼을 때만** 실행되는데, 그때가 실패 확률이 가장 높은 순간이다. 연결 경고 배너가 뜬 상태에서 보낸 메시지가 소리 없이 사라진다.

대조적으로 **메시지 수정·삭제는 `alert()`로 실패를 알린다.** 같은 앱 안에서 처리가 갈린다는 것이 문제의 성격을 보여준다 — 정책이 없고 그때그때 처리됐다.

## 3. 가짜

- **상태 메시지**(`SettingsModal`) — DB 컬럼이 없고, `sage-status` 값을 **다시 읽는 코드도 없다.** 쓰기만 하고 버려진다.
- **알림 토글 3개**(데스크톱·소리·멘션) — 백엔드·프론트 통틀어 알림 발송, `Notification`, `Audio` 사용이 **0건**. 켜도 아무 일도 일어나지 않는다.
- **저장 버튼의 이중성** — 진짜(이름·사진)와 가짜(상태·알림)를 한 번에 처리하고 동일한 `저장됨 ✓`를 띄운다. 가짜가 진짜 뒤에 숨어 의심조차 받지 않는다.

## 4. 죽음

- **`warping`**(`App.tsx:51`) — `setWarping`을 호출하는 코드가 프로젝트 어디에도 없다. 로그인→채팅 워프 연출(오라·콘텐츠 페이드·파티클 부스트)이 전부 살아 있는데 트리거만 없다. 로그인이 OAuth 리다이렉트로 바뀌면서 호출 지점이 사라진 것으로 보인다.

## 5. 깨끗한 것

- `lib/api.ts` — **미사용 함수 0개, 대응 엔드포인트 없는 함수 0개.** 배선 자체는 문제가 없다.
- 온보딩·프로필 화면의 백엔드 호출은 실패가 전부 인라인으로 표시된다.

## 6. 처리 결정

**이번에 한다**

| 항목 | 처리 | 이유 |
|---|---|---|
| 상태 메시지 | **제거** | 저장도 안 되고 읽는 곳도 없다. 진짜로 만들려면 컬럼·엔드포인트·노출 위치 설계가 필요한데 그만한 값이 없다 |
| 알림 토글 3개 | **제거** | 저장을 진짜로 만드는 문제가 아니라 **알림 기능 자체가 없다.** 권한 요청·소리·멘션 파싱이 선행돼야 한다 → 백로그의 "멘션+알림"과 함께 |
| `warping` | **되살린다** | 연출 코드가 전부 남아 있고 복원 비용이 삭제 비용과 비슷하다. OAuth 핸드오프 구간에서 트리거한다 |
| 온보딩 문구 | **수정** | `고른 사진은 저장되지 않아요`가 조건 없이 읽혀, `시작하기`를 누르려는 사용자도 저장이 안 된다고 오해한다 |
| 랜딩 프로필 진입점 | **추가** | 설정 모달이 이미 분기 바깥에 렌더돼 있어 트리거만 없다. 랜딩에서 프로필을 못 바꾸는 것은 기능 갭이다 |

**이번에 하지 않는다**

- **방 나가기 UI** — 백엔드 `DELETE /api/chatrooms/{id}/members`는 동작하지만 프론트에 호출부가 없다. 그런데 `GET /api/chatrooms`가 **멤버십과 무관하게 전체 방을 반환**하고(`ChatRoomController:48`), 방을 다시 누르면 `joinChatRoom`이 자동 재가입시킨다. 지금 버튼을 만들면 나가도 목록에 그대로 남아 "가짜 UI"를 하나 더 만드는 셈이다. **비공개방(인가) 작업과 함께 해야 의미가 생긴다.**
- **실패 표시 통일** — §2의 6개 경로. 값이 가장 크지만 공용 알림 표시를 설계해야 하고, 특히 메시지 전송은 낙관적 UI라 "전송 실패 상태 + 재시도"가 필요하다. 별도 설계로 다룬다.

## 7. 남는 것

- §2의 실패 무음 6개는 그대로 남는다. 이번 범위는 "거짓말하는 UI 제거"이고, "실패를 알리는 UI 추가"는 다음이다.
- 알림 기능은 백로그의 멘션과 묶여 있다. 멘션은 닉네임에 유니크 제약이 없어 **member id 참조로 저장**해야 한다는 선행 결정이 이미 있다.
