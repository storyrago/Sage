# 프로필 사진 — 온보딩 추가와 확정 방식 통일 설계

- 작성일: 2026-07-30
- 범위: `frontend/src/components/Onboarding.tsx`, `frontend/src/components/SettingsModal.tsx`, 공유 훅 신설. **백엔드 변경 없음.**
- 선행 작업: `docs/superpowers/specs/2026-07-29-onboarding-design.md` (온보딩 화면·API)
- 별도 작업으로 분리: S3 정리 정책 (§7)

## 1. 배경과 목표

두 가지를 함께 다룬다.

**하나. 온보딩 화면에서 사진을 바꿀 수 없다.** provider가 준 사진을 원형으로 보여주기만 한다(`Onboarding.tsx:68`). 선행 설계 D2가 "첫 관문의 입력은 닉네임 하나"로 정한 결과인데, 첫 화면에서 프로필을 한 번에 정리하고 싶은 사용자는 설정 화면을 따로 찾아가야 한다.

**둘. 설정 모달 안에서 저장 시점이 두 가지로 갈린다.** 닉네임·상태·알림은 `저장` 버튼을 눌러야 반영되는데, **사진만 파일을 고르는 즉시 업로드·저장된다**(`SettingsModal.tsx:54`). 같은 모달에서 어떤 항목은 확정이 필요하고 어떤 항목은 아니다.

목표는 **두 화면 모두 "확정을 눌러야 반영된다"로 통일**하고, 그 과정에서 중복될 로직을 한 곳에 모으는 것이다.

재료는 이미 있다.

| 함수 | 위치 | 역할 |
|---|---|---|
| `uploadImage(token, file)` | `frontend/src/lib/api.ts` | S3 업로드 후 URL 반환 |
| `updateProfileImage(token, url)` | `frontend/src/lib/api.ts` | 회원의 프로필 이미지 URL 갱신 |

백엔드는 온보딩 미완료 회원의 API를 막지 않으므로(선행 설계 D1), 온보딩 화면에서도 그대로 호출할 수 있다.

## 2. 결정 사항

**D1. 사진은 확정 버튼을 눌러야 반영된다.**
파일을 고르는 시점에는 서버를 호출하지 않고 로컬 미리보기만 만든다. 온보딩은 `시작하기`, 설정은 `저장`이 확정 지점이다.

*대가*: 설정 화면의 기존 동작(즉시 반영)이 바뀐다. 사진을 고른 뒤 `저장`을 누르지 않고 모달을 닫으면 반영되지 않는다. 이전에는 반영됐다.

**D2. 확정 시 순서는 사진 → 닉네임 → (온보딩은) 온보딩 기록이다.**

```
온보딩:  uploadImage → updateProfileImage → updateNickname → completeOnboarding → onDone
설정:    uploadImage → updateProfileImage → updateNickname → 로컬 설정 저장
```

온보딩 기록이 **마지막**이다. 중간에 실패하면 온보딩이 완료로 남지 않아 사용자가 다시 시도할 수 있다. 선행 설계에서 닉네임 수정과 온보딩 기록을 API 두 개로 나눈 이유와 같은 원칙이다.

**D3. 업로드에 성공한 URL은 캐시해 재시도 시 재사용한다.**
사진은 올라갔는데 닉네임 저장이 실패하는 부분 실패가 가능하다. 이때 사용자가 다시 확정 버튼을 누르면 **S3에 다시 올리지 않고** 캐시된 URL로 이어간다. 파일을 새로 고르면 캐시를 버린다.

`updateProfileImage`는 같은 URL로 다시 호출해도 결과가 같으므로 재시도에 안전하다.

**D4. 실패는 인라인 오류로 표시한다.**
설정 화면은 사진 실패를 `alert()`로 알리는데(`SettingsModal.tsx:63`), 닉네임 실패는 인라인 텍스트로 표시한다. 한 모달 안에서 두 방식이 섞이지 않도록 사진도 인라인으로 바꾼다. 오류 표시 위치는 **항목별로 나눈다** — 사진 오류는 아바타 아래, 닉네임 오류는 입력 아래. 어느 항목이 실패했는지 바로 보이게 하기 위해서다.

**D5. 파일 크기와 형식을 업로드 전에 검증한다.**
10MB를 넘거나 이미지가 아니면 요청을 보내지 않고 인라인 오류를 낸다. 백엔드 `spring.servlet.multipart.max-file-size: 10MB`, nginx `client_max_body_size 10m`와 같은 기준이다. 서버까지 갔다가 실패하면 큰 파일을 올리는 시간을 버리고 오류 메시지도 덜 친절하다.

**D6. 확정하지 않고 떠나면 고른 사진은 버린다.**
온보딩의 `나중에 하기`, 설정 모달의 닫기·Escape·배경 클릭이 모두 여기 해당한다. 온보딩에서는 사용자가 놀라지 않도록 건너뛰기 버튼 아래에 흐린 텍스트로 `고른 사진은 저장되지 않아요`를 조건부 표시한다. 확인 다이얼로그는 두지 않는다 — 되돌릴 수 없는 손실이 아니고(다시 고르면 된다) 첫 진입의 마찰을 늘린다.

안내 문구의 조건은 "파일을 고름"이 아니라 **"파일을 골랐고 아직 서버에 반영되지 않음"**이다. D2의 부분 실패 경로에서 사진 저장(`updateProfileImage`)까지는 성공하고 닉네임 저장이 실패할 수 있는데, 그 상태에서 `나중에 하기`를 누르면 사진은 **이미 반영되어 있다.** 이때 문구를 띄우면 거짓 안내가 된다.

**D7. 미리보기 ObjectURL은 명시적으로 해제한다.**
파일을 교체할 때, 확정을 마쳤을 때, 화면·모달을 떠날 때 `URL.revokeObjectURL`을 호출한다.

**D8. 두 화면이 공유하는 로직은 훅 하나로 모은다.**
D1·D3·D5·D7은 두 화면에서 문자 그대로 같은 동작이다. 각각 구현하면 한쪽만 고쳐지는 종류의 버그가 생긴다.

`frontend/src/lib/useProfilePhotoDraft.ts`에 둔다. 이 저장소에는 `hooks/` 디렉터리가 없고 `lib/`에 비컴포넌트 모듈(`api.ts`, `avatar.ts`)이 모여 있으므로 그 관례를 따른다.

## 3. 공유 훅 인터페이스

```ts
useProfilePhotoDraft(token: string): {
  previewUrl: string;      // 고른 파일의 로컬 미리보기. 없으면 빈 문자열
  hasDraft: boolean;       // 고른 파일이 있고 아직 서버에 반영되지 않음 (D6 문구 조건)
  error: string;           // 크기·형식 검증 실패 또는 업로드·저장 실패 메시지
  pick(file: File): void;  // 검증 → 미리보기 생성. 이전 미리보기·업로드 캐시는 버린다
  commit(): Promise<string | null>;  // 확정. 반영된 URL, 고른 파일이 없으면 null
  reset(): void;           // 미리보기 해제 + 상태 초기화
}
```

- `commit()`은 고른 파일이 없으면 아무 요청도 보내지 않고 `null`을 반환한다. 사진을 건드리지 않은 사용자에게 불필요한 요청이 가지 않는다.
- `commit()`이 던지는 예외는 호출한 화면이 받아 자기 방식으로 표시한다. 훅은 `error`도 함께 채워 아바타 옆 표시에 쓴다.
- 내부 상태: 고른 파일, 미리보기 URL, 업로드 성공 URL 캐시(D3), 사진 반영 완료 여부(D6).
- 크기 상수는 훅에 두고 백엔드·nginx 설정을 근거로 주석을 남긴다.

## 4. 화면별 동작

**공통** — 미리보기 우선순위는 고른 파일 → `photoUrl`(provider 또는 저장된 사진) → 기존 기본 표시(온보딩은 아이콘, 설정은 기존 방식). 진입점은 원형 아바타를 클릭 가능하게 만들고 그 아래 `사진 변경` 텍스트 버튼(보조 텍스트 색 `#9AA8A0`). 숨긴 `<input type="file" accept="image/*">`를 연다. 저장 중에는 파일 선택과 버튼을 모두 비활성화한다.

**온보딩** — 기존 `busy` 상태를 그대로 쓴다. `시작하기`가 D2 순서를 실행하고, 실패하면 화면을 유지한 채 인라인 오류를 띄운다. `나중에 하기`는 `completeOnboarding`만 호출하며, D6 조건이면 안내 문구를 함께 보여준다.

**설정** — `handlePhoto`가 즉시 업로드·저장하던 것을 `pick()` 호출로 바꾼다. `handleSave`가 사진 확정을 먼저 하고(성공 시 `onUpdatePhoto(url)`로 App 상태 갱신) 그다음 닉네임, 그다음 로컬 설정(상태 메시지·알림)을 저장한다. 사진 확정이 실패하면 닉네임 저장으로 넘어가지 않고 멈춘다. 모달을 닫거나 다시 열 때 `reset()`을 부른다 — 기존에 `name`을 되돌리는 `useEffect`가 있으므로 같은 자리에 넣는다.

**디자인 토큰**: 선행 설계와 같다 — 카드 `#1C241F` / `1px solid #2D362F` / radius 22, 본문 `#E6ECE8`, 보조 `#9AA8A0`, 흐린 `#6B7972`.

## 5. 검증

- `cd frontend && npm run lint && npm run build`
- 실제 업로드는 S3 자격증명이 필요하므로 로컬에서 재현하지 않는다. 배포 후 확인한다:
  - 온보딩에서 사진을 고르고 `시작하기` → 채팅 진입 후 사이드바·프로필에 새 사진, 새로고침해도 유지
  - 온보딩에서 사진만 고르고 `나중에 하기` → 사진이 저장되지 않고 provider 사진 유지, 안내 문구 노출
  - 설정에서 사진을 고르고 **저장하지 않고 닫기** → 반영되지 않음
  - 설정에서 사진과 닉네임을 함께 바꾸고 `저장` → 둘 다 반영, 새로고침해도 유지
  - 10MB 초과 파일 → 업로드 전에 오류 표시

## 6. 남는 것

- **설정 화면의 즉시 반영 동작이 사라진다**(D1의 대가). 사진 한 장만 바꾸려는 사용자도 `저장`을 눌러야 한다.
- **부분 실패 상태가 남을 수 있다.** 사진은 반영됐는데 닉네임 저장이 실패하면 그 상태로 화면에 머문다. 사용자가 다시 확정을 누르면 D3에 따라 재업로드 없이 이어간다.

## 7. 별도 작업 — S3 정리 정책

이번 범위에 넣지 않는다. 백엔드 코드와 AWS 콘솔의 수명주기 규칙이 함께 필요해 프론트와 독립적으로 다루는 편이 안전하다.

**확인된 사실** (`S3Service.java:27`):
- 키가 `{uuid}_{원본파일명}`으로 **버킷 루트에 평평하게** 쌓인다. prefix 구분이 없다.
- `/api/images`는 **채팅 이미지와 프로필 사진이 공용**이다.
- 삭제 코드가 어디에도 없다.

**두 종류의 누수**:

| 문제 | 성격 | 해법 |
|---|---|---|
| 교체된 옛 프로필 사진 | 사진을 바꿀 때마다 확실히 발생. 영구히 남는다 | 교체 시 옛 객체에 `orphan` 태그 → 수명주기 규칙이 N일 뒤 만료 |
| 확정 안 된 업로드 | 부분 실패·이탈 시 발생 | 업로드를 `pending/` prefix로 → 확정 시 정식 위치로 이동, `pending/`은 단기 만료 |

**진행 순서**: 교체된 옛 사진부터 다룬다. 코드가 적고 효과가 확실하다. `pending/` 도입은 업로드 경로 전체(채팅 이미지 포함)를 바꾸므로 그다음에 별도로 판단한다.

즉시 삭제가 아니라 **태그 + 수명주기**를 쓰는 이유는 복구 창을 남기기 위해서다. 버그로 잘못된 URL이 저장된 경우 즉시 삭제한 객체는 되돌릴 수 없다.
