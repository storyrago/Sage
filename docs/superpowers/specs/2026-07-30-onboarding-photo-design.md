# 온보딩 화면에서 프로필 사진 변경 설계

- 작성일: 2026-07-30
- 범위: `frontend/src/components/Onboarding.tsx` 한 화면. 백엔드 변경 없음.
- 선행 작업: `docs/superpowers/specs/2026-07-29-onboarding-design.md` (온보딩 화면·API)

## 1. 배경과 목표

온보딩 화면은 provider가 준 프로필 사진을 원형으로 보여주기만 하고 바꿀 수 없다(`Onboarding.tsx:68`). 사진 변경은 설정 화면에만 있다. 선행 설계 D2가 "첫 관문의 입력은 닉네임 하나"로 정한 결과다.

이번에는 그 결정을 뒤집어 **온보딩에서도 사진을 바꿀 수 있게** 한다. 첫 화면에서 프로필을 한 번에 정리하고 싶은 사용자가 설정 화면을 따로 찾아가지 않아도 되게 하는 것이 목표다.

재료는 이미 있다.

| 함수 | 위치 | 역할 |
|---|---|---|
| `uploadImage(token, file)` | `frontend/src/lib/api.ts` | S3 업로드 후 URL 반환 |
| `updateProfileImage(token, url)` | `frontend/src/lib/api.ts` | 회원의 프로필 이미지 URL 갱신 |

백엔드는 온보딩 미완료 회원의 API를 막지 않으므로(선행 설계 D1), 두 API를 온보딩 화면에서 그대로 호출할 수 있다.

## 2. 결정 사항

**D1. 사진은 `시작하기`를 눌러야 확정된다.**
파일을 고르는 시점에는 서버를 호출하지 않고 로컬 미리보기만 만든다. 확정 전에는 아무것도 바뀌지 않는다는 규칙을 화면 전체에 일관되게 적용한다.

*대가*: 설정 화면은 파일을 고르는 즉시 업로드·저장한다(`SettingsModal.tsx:54`). 두 화면의 동작이 달라진다. 또한 제출 시 요청이 여러 개 묶이므로 부분 실패 상태를 다뤄야 한다(D3).

**D2. 제출 순서는 사진 → 닉네임 → 온보딩 기록이다.**

```
uploadImage → updateProfileImage → updateNickname → completeOnboarding → onDone
```

온보딩 기록이 **마지막**이다. 중간에 실패하면 온보딩이 완료로 남지 않아 사용자가 다시 시도할 수 있다. 선행 설계에서 닉네임 수정과 온보딩 기록을 API 두 개로 나눈 이유와 같은 원칙이다.

**D3. 업로드에 성공한 URL은 캐시해 재시도 시 재사용한다.**
사진은 올라갔는데 닉네임 저장이 실패하는 부분 실패가 가능하다. 이때 사용자가 다시 `시작하기`를 누르면 **S3에 다시 올리지 않고** 캐시된 URL로 이어간다. 파일을 새로 고르면 캐시를 버린다.

`updateProfileImage`는 같은 URL로 다시 호출해도 결과가 같으므로 재시도에 안전하다.

**D4. 실패는 이 화면의 인라인 오류로 표시한다.**
설정 화면은 사진 실패를 `alert()`로 알리지만(`SettingsModal.tsx:63`), 온보딩 화면은 이미 인라인 오류 텍스트를 쓰고 있다. 한 화면 안에서 두 방식이 섞이지 않게 인라인으로 통일한다.

**D5. 파일 크기를 업로드 전에 검증한다.**
10MB를 넘으면 요청을 보내지 않고 인라인 오류를 낸다. 백엔드 `spring.servlet.multipart.max-file-size: 10MB`, nginx `client_max_body_size 10m`와 같은 기준이다. 서버까지 갔다가 실패하면 큰 파일을 업로드하는 시간을 버리고 오류 메시지도 덜 친절하다.

*범위 밖*: 설정 화면에는 이 검증이 없다. 이번에 함께 넣지 않는다.

**D6. `나중에 하기`는 확정되지 않은 사진을 버린다.**
D1의 정의상 `시작하기`를 거치지 않은 사진은 저장되지 않는다. 사용자가 놀라지 않도록, 건너뛰기 버튼 아래에 흐린 텍스트로 `고른 사진은 저장되지 않아요`를 조건부 표시한다. 확인 다이얼로그는 두지 않는다 — 되돌릴 수 없는 손실이 아니고(설정 화면에서 다시 올리면 된다) 첫 진입의 마찰을 늘린다.

안내 문구의 조건은 "파일을 고름"이 아니라 **"파일을 골랐고 아직 서버에 반영되지 않음"**이다. D2의 부분 실패 경로에서 사진 저장(`updateProfileImage`)까지는 성공하고 닉네임 저장이 실패할 수 있는데, 그 상태에서 사용자가 `나중에 하기`를 누르면 사진은 **이미 반영되어 있다.** 이때 문구를 그대로 띄우면 거짓 안내가 된다. 사진 저장 성공 여부를 별도 상태로 들고 그 경우에는 문구를 감춘다.

**D7. 미리보기 ObjectURL은 명시적으로 해제한다.**
파일을 교체할 때와 화면을 떠날 때 `URL.revokeObjectURL`을 호출한다.

## 3. 화면 동작

**미리보기 우선순위**: 고른 파일 → `user.photoUrl`(provider 사진) → 기본 아이콘

**진입점**: 기존 64px 원형 아바타를 클릭 가능하게 만들고, 그 아래에 `사진 변경` 텍스트 버튼(보조 텍스트 색 `#9AA8A0`)을 둔다. 숨긴 `<input type="file" accept="image/*">`를 연다.

**저장 중**: 파일 선택, `시작하기`, `나중에 하기`를 모두 비활성화한다. 이미 `busy` 상태가 있으므로 그대로 쓴다.

**디자인 토큰**: 선행 설계와 같다 — 카드 `#1C241F` / `1px solid #2D362F` / radius 22, 본문 `#E6ECE8`, 보조 `#9AA8A0`, 흐린 `#6B7972`.

## 4. 상태

| 상태 | 용도 |
|---|---|
| `file: File \| null` | 고른 파일. 제출 시 업로드 대상이자, D6 안내 문구의 조건 |
| `previewUrl: string` | `URL.createObjectURL(file)`. D7에 따라 해제 |
| `uploadedUrl: string` | S3 업로드 성공 URL 캐시(D3) |
| `photoSaved: boolean` | `updateProfileImage`까지 성공했는지. D6 안내 문구를 감추는 조건 |

기존 `nickname`, `error`, `busy`는 그대로 쓴다.

## 5. 검증

- `cd frontend && npm run lint && npm run build`
- 실제 업로드는 S3 자격증명이 필요하므로 로컬에서 재현하지 않는다. 배포 후 확인한다:
  - 사진을 고르고 `시작하기` → 채팅 진입 후 사이드바·프로필에 새 사진, 새로고침해도 유지
  - 사진만 고르고 `나중에 하기` → 사진이 저장되지 않고 provider 사진이 그대로
  - 10MB 초과 파일 → 업로드 전에 오류 표시

## 6. 남는 것

- **설정 화면과 동작이 다르다.** 설정은 즉시 반영(D1의 대가). 두 화면을 하나로 맞추려면 설정 화면도 확정 방식으로 바꿔야 하는데, 그건 이번 범위 밖이다.
- **설정 화면에는 파일 크기 사전 검증이 없다**(D5). 같은 개선이 필요하면 별도 작업으로 한다.
- **업로드된 뒤 버려지는 객체가 생길 수 있다.** 사진 업로드에는 성공했는데 사용자가 그대로 화면을 이탈하면 S3에 참조되지 않는 객체가 남는다. 현재 설정 화면도 같은 성질을 갖는다(업로드 후 저장 실패 시). 정리 정책은 이번 범위 밖이다.
