# 소셜 로그인 토큰 전달을 일회용 코드로 바꾸기

- 상태: 확정
- 선행: `2026-08-02-token-revocation-design.md`(D3 — 토큰 발급 경로는 회원 단위 무효화를 해제한다)
- 범위: 백엔드 + 프론트 OAuth 핸드오프. 스키마 변경 없음

## 1. 배경과 목표

소셜 로그인이 끝나면 `OAuth2SuccessHandler`가 JWT를 URL에 실어 프론트로 리다이렉트한다.

```java
response.sendRedirect(frontendUrl + "/#token=" + token);   // OAuth2SuccessHandler.java:40
```

`#` 뒤(fragment)는 브라우저가 서버로 보내지 않고, 프론트도 `history.replaceState`로 즉시 지운다(`App.tsx:161`). 거기까지는 의도대로다.

**문제는 그 리다이렉트를 만드는 302 응답의 `Location` 헤더다.** 거기에는 JWT가 통째로 들어 있고, 그 응답은 nginx를 지나 브라우저로 간다. 즉 **nginx 액세스 로그, 백엔드 액세스 로그, APM 트레이스에 JWT 전문이 남을 수 있다.** 로그를 읽을 수 있는 사람이나 로그가 새는 경로가 그대로 계정 탈취 경로가 된다.

토큰은 1시간짜리이고 지금은 로그아웃·탈퇴로만 무효화된다. 로그에서 주운 토큰은 그 시간 내내 유효하다.

**목표:** 리다이렉트에 자격증명을 싣지 않는다. 로그에 남아도 무의미한 값만 URL로 보내고, 토큰은 응답 본문으로만 전달한다.

## 2. 결정

**D1. 리다이렉트에는 일회용 코드를 싣고, 코드는 Redis에 60초 TTL로 둔다.**

| 키 | 값 | TTL |
|---|---|---|
| `oauth:code:{code}` | `memberId` | 60초 |

리다이렉트 → 프론트 부팅 → 교환 요청이 그 안에 끝난다. 모바일 저속 회선에도 여유가 있다. 길수록 로그에서 코드를 주웠을 때의 창이 커지므로 넉넉하게 잡지 않는다.

**값은 `memberId`만 담는다.** 토큰 생성에 필요한 나머지는 교환 시점에 DB에서 읽는다. 리다이렉트와 교환 사이에 회원이 사라지면 조회에서 걸러진다.

**D2. 코드는 한 번만 쓸 수 있다. 소비는 원자적으로 한다.**

`StringRedisTemplate`의 `getAndDelete`(Redis `GETDEL`)를 쓴다. 조회와 삭제가 한 명령이라, 같은 코드로 동시에 들어온 교환 요청 두 개가 **둘 다 성공할 수 없다.**

읽고 나서 지우는 두 단계로 하면 그 사이가 경합 창이 된다. 코드가 로그에 남을 수 있다는 것이 이 설계의 전제이므로, 두 번째 사용은 반드시 실패해야 한다.

**D3. 코드는 `UUID.randomUUID()`다.**

122비트 난수이고 JDK가 `SecureRandom`으로 만든다. 60초 TTL에서 추측은 성립하지 않는다. 이 레포가 `jti`에 이미 같은 것을 쓴다.

**D4. 교환은 `POST /api/auth/oauth/token`이다. 코드는 본문으로 받는다.**

아직 토큰이 없는 상태에서 부르므로 인증이 필요 없다. `/api/auth/**`가 이미 `permitAll`이라(`SecurityConfig.java:50`) **인가 설정을 바꾸지 않는다.** 로그아웃 엔드포인트와 반대다 — 그쪽은 인증이 필요해서 permitAll 앞에 따로 등록해야 했다.

**코드를 쿼리 파라미터로 받지 않는다.** 그러면 그 코드가 다시 액세스 로그에 남아 옮긴 의미가 절반 사라진다. 응답도 본문으로 나가므로 토큰이 로그에 남지 않는다.

응답은 기존 `LoginResponse`를 재사용한다. 새 DTO를 만들지 않는다.

**D5. 토큰 발급이 `OAuth2SuccessHandler`에서 교환 지점으로 옮겨간다.**

이 이동에 딸린 것이 하나 있다. 토큰 무효화 설계 D3은 **토큰을 발급하는 모든 경로가 회원 단위 무효화 키를 지워야 한다**고 정했고, `OAuth2SuccessHandler`가 지금 그것을 한다(`OAuth2SuccessHandler.java:38`).

발급이 옮겨가면 `clearMember`도 함께 옮겨야 한다. 남겨두면 리다이렉트 시점에 키를 지우고 교환 시점에 토큰을 만들게 되어, 그 사이에 무효화가 걸리면 방금 발급한 토큰이 거부된다.

발급 경로는 여전히 둘이다 — `AuthService.login`(이메일·비밀번호)과 교환. `OAuth2SuccessHandler`는 발급에서 빠진다.

**D6. `#token=`를 남기지 않는다.**

프론트와 백엔드가 같은 배포로 함께 나가므로 과도기가 없다. 남겨두면 노출 경로가 그대로 열려 있는 것이라 이 작업의 목적이 사라진다.

*대가*: 배포 순간에 OAuth 진행 중이던 사용자는 로그인이 실패한다. 다시 시도하면 된다. 창은 수 초다.

**D7. Redis가 죽으면 소셜 로그인이 실패한다(fail-closed).**

거부목록(`TokenDenylist`)과 반대 방향이다. 거기서는 통과시키지 않으면 서비스가 멈추지만, 여기서는 통과시킬 것이 없다 — 코드를 저장하지 못하면 로그인 자체가 성립하지 않는다. 삼키고 진행하면 사용자는 코드 없는 리다이렉트를 받고 원인을 알 수 없다.

이메일·비밀번호 로그인은 영향받지 않는다.

**D8. 코드 교환 실패는 구분하지 않는다.**

만료된 코드, 이미 쓴 코드, 존재한 적 없는 코드를 전부 같은 응답으로 돌려준다. 구분하면 공격자에게 "이 코드는 존재했다"를 알려주는 것이다. 기존 `ErrorCode.UNAUTHORIZED`(401)를 쓰고 **새 `ErrorCode`를 만들지 않는다.**

## 3. 구조

| 파일 | 변경 |
|---|---|
| `security/OAuthCodeStore.java` (신규) | 코드 발급·소비의 유일한 지점 |
| `security/OAuth2SuccessHandler.java` (수정) | 토큰 대신 코드를 싣는다. 발급·`clearMember`가 빠진다 |
| `controller/AuthController.java` (수정) | `POST /api/auth/oauth/token` |
| `service/AuthService.java` (수정) | `exchangeOAuthCode(code)` — 코드 소비 → `clearMember` → 토큰 발급 |
| `dto/OAuthCodeRequest.java` (신규) | 교환 요청 본문 |
| `frontend/src/lib/api.ts` (수정) | `exchangeOAuthCode(code)` |
| `frontend/src/App.tsx` (수정) | `#token=` 대신 `#code=`를 읽어 교환한다 |

`OAuth2FailureHandler`는 그대로 둔다. `#oauth_error=`가 싣는 것은 오류 코드이지 자격증명이 아니다.

`OAuthCodeStore`는 `StringRedisTemplate`을 쓴다 — 값이 문자열이고, `TokenDenylist`·`PresenceRegistry`가 같은 것을 쓴다.

## 4. 데이터 흐름

```
소셜 로그인 성공
  OAuth2SuccessHandler
    ├ 회원 조회
    ├ code = UUID
    ├ oauth:code:{code} = memberId, TTL 60초     ← 실패하면 로그인 실패(D7)
    └ 302 Location: {frontend}/#code={code}      ← 로그에 남아도 60초, 1회용

프론트
  #code= 읽음 → history.replaceState로 즉시 제거
  → POST /api/auth/oauth/token  { "code": "..." }    ← 본문. 로그에 안 남는다
  → 200 { "accessToken": "..." }                      ← 본문. 로그에 안 남는다
  → 기존 흐름(getMe → persistSession) 그대로

교환 (AuthService.exchangeOAuthCode)
  GETDEL oauth:code:{code}
    ├ 없음(만료·재사용·위조) → 401 UNAUTHORIZED
    └ memberId 획득
        ├ 회원 조회 (없으면 401)
        ├ clearMember(memberId)          ← 토큰 무효화 설계 D3
        └ createAccessToken → 응답 본문
```

## 5. 오류 처리

- **코드 저장 실패(Redis)** → 소셜 로그인을 실패로 응답한다. `OAuth2FailureHandler`와 같은 형태로 `#oauth_error=`를 실어 리다이렉트한다(D7).
- **코드 조회 실패(Redis)** → 예외를 그대로 올려 500이 되게 한다. **잘못된 코드(401)와 구분한다** — 서버가 고장난 것이지 사용자가 잘못한 것이 아니고, "다시 로그인해 주세요"는 이 상황에서 통하지 않는 안내다. 500은 코드의 존재 여부를 알려주지 않으므로 D8을 해치지 않는다.
- **코드 없음·만료·재사용** → 전부 401 `UNAUTHORIZED`. 구분하지 않는다(D8).
- **코드는 있는데 회원이 없음** → 같은 401. 리다이렉트와 교환 사이에 탈퇴한 경우다.
- **프론트** → 401을 받으면 기존 `#oauth_error=` 경로와 같은 안내를 띄운다. "소셜 로그인에 실패했어요. 다시 시도해 주세요." **5xx는 구분해 안내한다** — "지금 로그인 서버에 문제가 있어요. 잠시 후 다시 시도해 주세요." 위에서 500을 401과 나눈 이유가 여기서 쓰인다. 사용자가 다시 시도해도 해결되지 않는 상황에 "다시 시도해 주세요"만 띄우면 계층을 나눈 것이 무의미해진다.

## 6. 남기는 한계

- **코드는 여전히 URL에 있다.** 로그·브라우저 히스토리·리퍼러에 남을 수 있다. 60초 TTL과 1회용이 그 값을 무의미하게 만드는 것이지, URL에 아무것도 안 싣는 것은 아니다. 완전히 없애려면 백엔드가 프론트와 같은 오리진에서 `httpOnly` 쿠키를 세우는 구조여야 하고, 그것은 리프레시 토큰 도입과 함께 다룰 일이다.
- **코드를 발급 대상에 묶지 않는다.** IP·User-Agent 대조를 하지 않는다. 60초·1회용·122비트 난수면 실효 위험이 낮고, 모바일 네트워크 전환에서 오탐이 난다.
- **Redis 장애 중에는 소셜 로그인이 불가하다**(D7의 대가). 이메일 로그인은 계속 된다.
- **액세스 토큰 자체의 수명은 그대로 1시간이다.** 이 작업은 전달 경로만 바꾼다. 짧은 액세스 토큰 + 리프레시 토큰은 별도 작업이고, 이 설계는 그 방향을 막지 않는다 — 그때 이 교환 지점이 리프레시 토큰까지 함께 내려주는 자리가 된다.

## 7. 검증

**자동 테스트**

- 소셜 로그인 성공 시 리다이렉트 URL에 `#code=`가 실리고 **JWT가 실리지 않는다**
- 발급된 코드로 교환하면 액세스 토큰이 나온다
- **같은 코드를 두 번 교환하면 두 번째는 401이다**(1회용)
- 존재하지 않는 코드는 401이다(Redis TTL 만료는 키 삭제와 동일하므로, 만료된 코드도 이 상태로 덮인다 — TTL 값 자체는 `OAuthCodeStoreTest.코드의_TTL은_60초다`가 고정한다)
- 교환이 그 회원의 회원 단위 무효화 키를 지운다(토큰 무효화 설계 D3)
- 교환은 인증 없이 호출할 수 있다
- 코드에 담긴 회원이 사라졌으면 401이다

**프론트 검증**: `npm run lint && npm test && npm run build`

- 옛 형식(`#token=`) 핸드오프를 받으면 해시를 지우고 실패를 안내한다(배포 전환·롤백 중 옛 백엔드 응답)

**배포 후 실측**

- 소셜 로그인 후 주소창에 토큰이 아니라 코드가 잠깐 보이는지(그리고 즉시 사라지는지)
- 그 코드를 복사해 다시 교환하면 401인지
- nginx 액세스 로그에 JWT 형태의 문자열이 더 이상 남지 않는지
- 구글·카카오 양쪽 모두 로그인이 되는지
