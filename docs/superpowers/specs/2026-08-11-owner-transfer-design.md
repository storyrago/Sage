# 방장 위임 설계

2026-08-11

## 1. 목표

주인이 **남은 멤버 중 후계자를 지정하고** 그 방을 나갈 수 있게 한다.

비공개방 2단계가 `OWNER_CANNOT_LEAVE`를 넣었는데 탈출구가 방 삭제 하나뿐이었다. 방을 지우지 않고 손을 떼려면 넘길 사람을 고를 수 있어야 한다.

## 2. 이 작업이 풀지 않는 것

**주인 없는 방을 되살리지 않는다.** 위임은 현재 주인이 하는 행동이라, 주인이 없는 방(시드 방, 주인이 탈퇴한 방)에는 쓸 수 없다. 그 방들은 방 데이터를 초기화하면서 사라진다.

**계정 탈퇴는 현행을 유지한다.** 지금은 소유 방의 주인·코드를 회수해 동결한다(`releaseOwnedRooms`). 탈퇴할 때 방마다 후계자를 고르게 하면 탈퇴 흐름이 무거워지고, 소유 방이 여럿이면 탈퇴 화면이 방 목록이 된다. 탈퇴는 드물고 되돌릴 수 없는 행동이라 지금의 자동 동결이 더 안전하다. 그 경로는 이미 검증돼 있어 건드리면 그 테스트들을 흔든다.

따라서 **앞으로 주인 없는 방이 생기는 경로는 계정 탈퇴 하나만 남는다.**

## 3. API

### `PATCH /api/chatrooms/{id}/owner`

요청 본문: `{ "memberId": 42 }`
응답: `ChatRoomResponse` — 요청자는 이제 주인이 아니므로 `owner: false`, `inviteCode` 키 없음

판정 순서:

| 상황 | 결과 |
|---|---|
| 삭제된 방 | `CHAT_ROOM_NOT_FOUND` 404 |
| 요청자가 주인이 아님 (`created_by`가 `NULL`인 방 포함) | `NOT_ROOM_OWNER` 403 |
| 대상이 그 방의 현재 멤버가 아님 | `NOT_JOINED_ROOM` 403 |
| 대상이 요청자 자신 | `INVALID_INPUT_VALUE` 400 |

- **차단된 사람은 멤버가 아니므로** 멤버 검사에서 자연히 걸린다. 별도 검사를 두지 않는다.
- 자기 자신 위임은 프론트가 목록에서 자신을 빼서 도달하지 않지만, 서버가 마지막 방어선이다. 새 `ErrorCode`를 만들지 않고 `INVALID_INPUT_VALUE`로 둔다 — 정상 경로로 도달할 수 없는 입력이라 전용 문구의 값어치가 없다.
- **본문은 `@RequestBody(required = false)`로 받고 `memberId`가 없으면 `INVALID_INPUT_VALUE`로 거부한다.** PR #102가 `HttpMessageNotReadableException` 핸들러를 넣어 본문 없는 요청도 이제 400이 되지만, 명시적으로 거부하는 편이 의도가 드러난다.

## 4. 도메인

`ChatRoom`에 변경 메서드 하나를 더한다. 2단계가 만든 `softDelete()`·`makePublic()`·`makePrivate()`와 같은 형태다.

```java
public void transferOwnership(Member newOwner) {
    this.createdBy = newOwner;
}
```

**잠긴 방은 위임과 함께 코드도 새로 뽑는다.** 서비스가 `transferOwnership` 직후
`chatRoom.isPrivate()`이면 기존 `nextUnusedCode()`로 `reissueInviteCode()`를 호출한다.
바로 옆 `setPrivate`가 전환마다 코드를 새로 뽑는 것과 같은 이유다 — 옛 코드가 살아있으면
방을 통제하지 못하게 된 옛 주인이 그 뒤로도 유효한 입장 코드를 계속 쥔다. 위임은
`setPrivate`보다 큰 신뢰 경계 이동이라 같은 원칙이 더 강하게 적용된다.

**대가**: 새 주인이 유지하고 싶었던 기존 초대 링크도 함께 죽는다. 위임 직후 새 주인이
새 코드를 다시 공유해야 한다.

공개방은 코드가 없으므로 해당 없다.

## 5. 위임 후 나가기

**따로 만들 것이 없다.** `created_by`가 바뀌는 순간 기존 `leave`의 `OWNER_CANNOT_LEAVE` 가드가 자연히 통과한다. 새 엔드포인트도, 새 오류 코드도, 새 분기도 필요 없다.

옛 주인은 위임 후 일반 멤버이므로 평범하게 나갈 수 있고, 나갈 때 기존 `RoomLeftEvent(ROOM_MEMBERSHIP_REVOKED)` 경로를 그대로 탄다.

## 6. 실시간 통지 — 만들지 않는다

새 주인은 다음 방 목록 갱신 때 `owner: true`로 바뀌어 방장 패널이 나타난다. 2단계가 랜딩 복귀(`onGoHome`)와 WS 재연결에 `refreshRooms`를 넣어 뒀으므로 자연히 갱신된다.

**대가**: 새 주인이 화면 어딘가에 가만히 앉아 있으면 다음 갱신까지 자기가 주인이 된 걸 모른다.

통지를 만들려면 새 개인 큐 목적지를 뚫어야 한다. 기존 `/queue/errors`는 이름 그대로 오류 통지용이고, 프론트의 `onAuthzError`가 그것을 받아 **방 상태를 정리하고 랜딩으로 돌린다** — 위임 성공을 그 채널로 보내면 새 주인 화면이 정리당한다. 성격이 정반대라 재사용할 수 없다. 그 값어치가 지금은 없다고 판단한다.

## 7. 프론트

확대한 우표의 방장 패널에 "방장 넘기기"를 더한다.

- 참가자 목록은 이미 있는 `getRoomMemberProfiles`로 가져오고 **자기 자신을 뺀다.**
- **확인 단계가 필수다 — 되돌릴 수 없다.** 넘기는 순간 내 방장 권한이 사라지고, 되돌리려면 새 주인이 다시 넘겨줘야 한다. 확인 문구에 그 사실을 적는다.
- 위임 성공 후 `refreshRooms`를 부른다. 그 방의 `owner`가 `false`가 되어 방장 패널이 사라진다.
- 멤버가 자기 혼자면 넘길 대상이 없다. 그 경우 "넘길 수 있는 참가자가 없어요"를 보여준다 — 버튼만 두고 눌렀을 때 빈 목록을 보여주면 왜 안 되는지 알 수 없다.
- 기존 방장 액션들과 같은 `ownerBusy` 패턴을 따르고, 확인 state는 `focusedId` 변경 시 초기화하는 기존 이펙트에 함께 넣는다.

## 8. 검증

- 위임 후 **옛 주인이 실제로 방을 나갈 수 있는지**(`OWNER_CANNOT_LEAVE`가 더 이상 안 나오는지)
- 위임 후 **새 주인이 방장 API를 쓸 수 있고 옛 주인은 못 쓰는지** — 권한이 실제로 옮겨갔는지는 이것으로만 확인된다
- 주인 없는 방(`created_by` NULL)에서 위임이 **403이고 500이 아닌지**
- 멤버가 아닌 사람에게 위임할 수 없는지
- 응답에서 **옛 주인에게 `inviteCode`가 더 이상 실리지 않는지** — 위임했는데 코드가 계속 보이면 권한 이양이 반쪽이다
- 프론트 `npm run lint && npm run build && npx vitest run`

## 9. 범위 밖

계정 탈퇴 시 후계자 지정, 주인 없는 방 되살리기(claim·자동 승계), 위임 실시간 통지, 위임 이력 기록.
