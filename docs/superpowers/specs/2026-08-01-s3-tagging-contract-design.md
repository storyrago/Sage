# S3 태깅 계약 설계 (PR 3)

- 상태: 확정
- 선행: `2026-07-30-s3-orphan-cleanup-design.md`(태깅 정책), `2026-07-31-room-authorization-design.md` §8(A10)
- 범위: 백엔드만. 스키마 변경 없음. 프론트 변경 없음

## 1. 배경과 목표

참조가 끊긴 S3 객체에 `orphan=true` 태그를 달고 수명주기 규칙이 30일 뒤 만료시킨다. 문제는 **무엇을 근거로 "참조가 끊겼다"고 판단하는가**다.

지금은 호출자가 그 순간 들고 있던 URL 문자열이 근거다. `tagAsOrphan(url)`의 유일한 게이트는 우리 버킷 URL인지 확인하는 접두사 검사뿐이고, 그 객체를 **아직 참조하는 행이 있는지는 묻지 않는다**.

프로필 이미지와 메시지 이미지 어디에도 URL 검증이 없어 같은 URL을 여러 행이 참조할 수 있다. 그래서 이 계약은 두 가지로 터진다.

- **정상 사용**: 같은 사진을 두 사람이 프로필로 쓰거나 같은 URL이 여러 메시지에 붙은 상태에서 한 쪽이 지워지면, 살아 있는 이미지에 만료 태그가 붙는다.
- **공격**: 남의 객체 URL을 자기 리소스에 붙였다 떼면 그 객체가 만료 예약된다. 프로필은 요청 2번, 메시지는 방 입장 + 요청 2번이면 재현된다.

**목표:** 태깅 판단의 근거를 호출자의 주장에서 DB 상태로 바꾼다.

## 2. 결정

**D1. 태깅 직전에 잔여 참조를 질의한다.**

`members.profile_image_url`, `messages.image_url`, `messages.content`(본문에 박힌 URL, 프론트가 하위호환으로 이미지 렌더링하는 대상)에 그 URL을 참조하는 행이 하나라도 있으면 태깅하지 않는다. 피해자 객체는 피해자 행이 여전히 참조하므로 태깅 대상이 되지 않는다. 같은 검사가 정상 사용의 공유 참조도 함께 막는다.

`Message.softDelete()`가 `imageUrl`을 `null`로 지우므로(`Message.java:75`) 소프트 삭제된 메시지가 살아 있는 참조로 잡히지 않는다.

**D2. 검사는 `ImageCleanupListener`에 둔다.**

프로필 교체와 메시지 삭제가 `ImageDereferencedEvent` 하나로 합류하는 지점이다. 여기에 두면 **구조적으로 모든 발행자가 검사를 지난다** — 나중에 세 번째 발행자가 생겨도 자동으로 적용된다.

`S3Service.tagAsOrphan`은 손대지 않는다. S3 어댑터가 DB를 알 이유가 없고, 우리 버킷 판별(선행 설계 D3)은 그대로 그 자리의 책임이다.

**D3. 판단은 한 곳에서만 한다.**

`ImageReferences.isReferenced(String url)`를 새로 만든다. `RoomAccess`가 멤버십 판정의 단일 지점인 것과 같은 자리다. 리스너는 이 답만 보고 태깅 여부를 정한다.

**D4. 회원 탈퇴도 태깅 경로에 연결한다.**

지금 `MemberService.delete`는 메시지를 벌크 삭제하고 회원을 지우면서 참조 해제 이벤트를 하나도 발행하지 않는다(`MemberService.java:74-83`). 탈퇴자의 프로필 사진과 이미지 메시지는 버킷에 영원히 남는다.

삭제 전에 그 회원의 프로필 URL과 이미지 메시지 URL을 모아 두고, 커밋 후 URL마다 이벤트를 발행한다. D1의 참조 검사를 그대로 지나므로 남이 쓰고 있는 URL은 태깅되지 않는다.

**D5. 참조 질의가 실패하면 태깅하지 않는다.**

예외를 삼키고 경고를 남긴 뒤 그 URL을 건너뛴다. 판단할 수 없을 때는 태깅하지 않는 쪽이 안전하다 — 잘못 태깅한 객체는 30일 뒤 사라지지만, 태깅하지 못한 객체는 저장 비용만 남는다.

URL이 여러 개인 탈퇴 경로에서 하나가 실패해도 나머지는 계속 처리한다.

## 3. 구조

| 파일 | 변경 |
|---|---|
| `service/ImageReferences.java` (신규) | `boolean isReferenced(String url)` — 참조 여부 판단의 유일한 지점 |
| `event/ImageCleanupListener.java` (수정) | 태깅 전 `isReferenced` 확인 |
| `repository/MemberRepository.java` (수정) | `boolean existsByProfileImageUrl(String url)` |
| `repository/MessageRepository.java` (수정) | `boolean existsByImageUrl(String url)`, `boolean existsByContentContaining(String url)`, 탈퇴용 이미지 URL 조회 |
| `service/MemberService.java` (수정) | `delete()`에서 프로필·메시지 이미지 URL마다 이벤트 발행 |

`ImageReferences`는 `S3Service`와 같은 `service` 패키지에 둔다(메인 코드에 `s3` 패키지가 없다). 새 이벤트 타입을 만들지 않는다 — `ImageDereferencedEvent` 하나를 계속 쓴다(선행 설계 D6).

## 4. 데이터 흐름

```
프로필 교체 / 메시지 삭제 / 회원 탈퇴
  └ ImageDereferencedEvent(url) 발행 → 커밋
      └ AFTER_COMMIT 리스너
          ├ imageReferences.isReferenced(url)
          │   ├ true  → 태깅하지 않는다 (누군가 아직 참조한다)
          │   └ false → s3Service.tagAsOrphan(url)
          └ 질의 실패 → 경고 후 건너뛴다
```

탈퇴는 이벤트가 여러 개다. 삭제 전에 URL을 모으고(프로필 1건 + 이미지 메시지 N건), 중복을 제거해 발행한다. 리스너는 각각을 독립적으로 처리한다.

## 5. 오류 처리

- **참조 질의 실패** → 경고를 남기고 그 URL은 태깅하지 않는다.
- **태깅 실패** → 선행 설계 D5 그대로 삼키고 경고를 남긴다. 정리는 부가 작업이지 본 작업이 아니다.
- **탈퇴 시 URL 여러 건** → 하나의 실패가 나머지를 막지 않는다.
- **우리 버킷이 아닌 URL** → `S3Service`가 접두사 검사로 걸러낸다(선행 설계 D3). 참조 질의는 그 전에 돌지만, 외부 CDN URL은 어차피 참조가 남아 있거나 태깅이 무시되므로 결과가 같다.

## 6. 남기는 한계

- **남의 URL을 자기 리소스에 붙이는 것 자체는 여전히 가능하다.** 프로필·메시지 저장에 URL 소유권 검증이 없다. 공개 버킷 URL이라 핫링크·사칭은 원래 열려 있던 성질이고, 이번 변경이 막는 것은 **남의 객체를 만료시키는 것**이다. 진짜 차단은 업로드 시 업로더를 기록하는 귀속 설계에 달려 있다 — 별도 과제.
- **질의와 태깅 사이에 창이 있다.** 참조가 0인 것을 확인한 직후 누군가 그 URL을 새로 참조하기 시작하면 태그가 붙은 채 남는다. 태그 제거 경로가 없다는 것은 선행 설계 §7의 한계 그대로다.
- **인덱스를 넣지 않는다.** `members.profile_image_url`·`messages.image_url`·`messages.content` 모두 인덱스가 없어 `EXISTS`가 풀스캔이다(`content`는 `LIKE` 검색이라 인덱스가 있어도 활용되지 않는다). 현재 규모에서는 무해하다. 메시지가 수십만 행이 되면 `image_url` 인덱스가 필요하다.
- **확정되지 않은 업로드는 여전히 남는다.** 업로드했지만 어디에도 붙이지 않은 객체는 참조가 애초에 없어 이벤트도 발생하지 않는다(선행 설계 §7).
- **이미 쌓인 누적분은 그대로다.** 이번 변경은 앞으로 발생하는 것만 처리한다.

## 7. 검증

**자동 테스트 — "태깅된다"가 아니라 "안 된다"를 본다.**

- 다른 회원이 같은 URL을 프로필로 쓰고 있으면 태깅하지 않는다
- 다른 메시지가 같은 URL을 참조하고 있으면 태깅하지 않는다
- 다른 메시지 본문에 그 URL이 포함되어 있으면 태깅하지 않는다
- 아무도 참조하지 않으면 태깅한다
- **공격 재현**: 남의 URL을 자기 프로필에 넣었다 다른 URL로 바꿔도 피해자 객체가 태깅되지 않는다
- **공격 재현**: 남의 URL을 자기 메시지에 붙였다 삭제해도 피해자 객체가 태깅되지 않는다
- 소프트 삭제된 메시지는 참조로 세지 않는다
- 탈퇴 시 프로필과 이미지 메시지 URL마다 이벤트가 발행된다
- 탈퇴자의 URL을 다른 사람이 참조 중이면 태깅되지 않는다
- 참조 질의가 실패하면 태깅하지 않고 예외를 밖으로 내보내지 않는다

기존 `S3OrphanTaggingTest`(우리 버킷 URL 판별)와 `ImageDereferenceEventTest`(이벤트 발행 조건)는 그대로 통과해야 한다. `S3Service`와 발행 조건을 바꾸지 않기 때문이다.

**배포 후 실측**

- 프로필 사진을 두 번 바꾸고, 옛 사진이 다른 곳에서 안 쓰이면 태그가 붙는지(S3 콘솔에서 객체 태그 확인)
- 같은 사진을 두 계정이 프로필로 쓰는 상태에서 한쪽이 바꾸면 태그가 붙지 않는지
- 이미지 메시지를 보내고 지우면 태그가 붙는지
- 탈퇴 후 그 회원의 이미지에 태그가 붙는지
